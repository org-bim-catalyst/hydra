# Migrations — production adoption procedure

`InitialCreate` was generated by EF Core as if the database were empty (this is a **new**
`AskLucyDbContext`, distinct from the legacy `ChatGPT_ClientContext`, even though both
point at the same physical database per `spec.md` FR-014). **Do not run
`dotnet ef database update` with this migration directly against the production
database** — the Identity tables it creates already exist there, and it would fail (or
worse, partially succeed) against a populated database.

This is exactly the risk flagged in `spec.md` § Risks ("the production migration script
must be tested against a copy of production data before running against the live
database") and `tasks.md` T010/T047. The required procedure, to be executed by someone
with real production database access — **not** automated in CI:

1. **Restore a copy** of the production database to a non-production environment.
2. **Baseline the copy**: since the copy already has the legacy schema, insert a row into
   `__EFMigrationsHistory` for `InitialCreate` (matching this migration's id/product
   version) **without** running its `Up()` — this tells EF Core "this schema state is
   already achieved," which is true for every table this migration defines except the two
   genuinely new/changed ones.
3. **Apply only the real deltas** by hand (or via a second, incremental migration
   generated after this baseline step) against the restored copy:
   - `CREATE TABLE RefreshTokens` (this table is genuinely new — no baseline needed for it).
   - Add `ApplicationUser.AvatarFileName`, migrate existing `ProfilePicture` BLOBs to files
     via the application's data-fix pass (`tasks.md` T011), then drop `ProfilePicture`.
   - Migrate `UserChats`: add the new `Id (uniqueidentifier)`/audit/soft-delete/concurrency
     columns, backfill `Id` via `NEWSEQUENTIALID()` and `CreatedBy = UserId` for existing
     rows, convert `CreationDateTime`/`LastAccessDateTime` to UTC into
     `CreatedAtUtc`/`ModifiedAtUtc`, then drop the old `int` identity `Id` and promote the
     new `Id` to primary key (research.md Topic 5).
4. **Verify** row-for-row parity between the restored copy's pre- and post-migration
   `UserChats`/`AspNetUsers` data (`quickstart.md` § 6) before touching production.
5. Repeat steps 2–3 against production only after step 4 passes, during the planned
   maintenance window (`spec.md` § Dependencies).

Once this baseline is in place, every *subsequent* migration (added after `InitialCreate`)
applies normally via `dotnet ef database update` — only this first adoption migration
needs the manual baseline treatment, because it is adopting Code-First migrations onto an
already-existing, hand-evolved schema.
