# Research: MCP (Model Context Protocol) Integration

**Feature**: [spec.md](./spec.md) | **Date**: 2026-08-10

This document resolves every open technical question the spec leaves open, grounded in the actual current state of the codebase — not the aspirational placeholder sketches in `docs/ARCHITECTURE.md` §16 ("MCP Tool Engine"), `docs/ENTITY_MODEL.md` §11 ("MCP Aggregate": `McpServer`/`McpTool`/`McpExecution`), `docs/DATABASE.md` §12, `docs/DOMAIN_SERVICES.md` §23 (`IMcpService`), and `docs/API_GUIDELINES.md` §27, all of which predate this spec and describe a simpler shape than this feature actually needs (most notably, none of them anticipate spec 020's Agent Framework existing first). Those sections are superseded by this plan and will be rewritten during implementation, not before — the same convention spec 020's own research.md established for its own superseded placeholders.

## Decision 1 — MCP tools compose into the existing compile-time `AgentToolCatalog`, not a second runtime

**Decision**: `AgentToolCatalog` (`src/AskLucy.Application/Agents/Tools/AgentToolCatalog.cs`) is extended to merge two sources instead of one: the existing DI-registered `IEnumerable<IAgentTool>` (native tools, unchanged) and a new `IMcpToolRegistry.ActiveTools` (an in-memory, singleton-scoped snapshot of `McpToolAdapter` instances — one per currently Active, currently-available MCP tool). `IMcpToolRegistry` exposes a synchronous `IReadOnlyCollection<IAgentTool> ActiveTools { get; }` backed by a `ConcurrentDictionary<string, IAgentTool>` that is rebuilt by a small refresh method invoked after every capability-refresh job run, every tool activation/deactivation, and every server enable/disable/removal — never by a per-call database read. `AgentToolCatalog.Find`/`AgentToolCatalog.All` remain synchronous and callers (`AgentExecutionOrchestrator.ResolveAvailableTools`, `AgentPlanner`) require zero changes beyond the constructor now also depending on `IMcpToolRegistry`.

**Rationale**: spec 020's research.md Decision 10 explicitly deferred dynamic tool discovery to "MCP... explicitly out of scope for this feature" — this is that exact deferred work. FR-019 forbids the Agent Runtime branching on native-vs-MCP; the cleanest way to guarantee that structurally (not just by convention) is for both sources to already be plain `IAgentTool` instances by the time `AgentToolCatalog` sees them, so every downstream consumer (planner, orchestrator, permission/approval/duplicate-call-detection logic) is unmodified. Keeping the registry's read path synchronous and in-memory satisfies FR-012 ("cache discovered capability metadata rather than rediscovering it on every agent execution") for free — a cache miss is structurally impossible on the hot path.

**Alternatives considered**: (a) Have `AgentToolCatalog.Find` become `async` and query the database directly — rejected; it would force every existing synchronous call site in the orchestrator/planner to change, a much larger blast radius than adding one new constructor dependency, and re-introduces a per-call I/O cost FR-012 explicitly warns against. (b) A separate `IMcpToolCatalog` the orchestrator checks only when the native catalog misses — rejected; that *is* the "branches on native vs MCP" logic FR-019 forbids.

## Decision 2 — Protocol/transport via the official MCP C# SDK, wrapped behind Application-owned interfaces

**Decision**: `Infrastructure.Mcp` (a new `src/AskLucy.Infrastructure/Mcp/` folder — no new project) takes a dependency on the official `ModelContextProtocol` NuGet SDK and implements two Application-owned interfaces: `IMcpClientFactory` (resolves/creates a connected client for a given `McpServerId`, handling transport selection, authentication, and connection reuse) and `IMcpClient` (the thin per-server operation surface: `ListToolsAsync`, `ListResourcesAsync`, `ListPromptsAsync`, `CallToolAsync`, `ReadResourceAsync`, `GetPromptAsync`, plus a lightweight `PingAsync` for health checks). `Application`/`Domain` reference only `IMcpClient`/`IMcpClientFactory`; no SDK type crosses that boundary.

**Rationale**: Constitution §3 forbids `Application` referencing a concrete SDK, and §2.VII (Convention over Configuration) disfavors reinventing JSON-RPC framing, Streamable HTTP semantics, and capability negotiation that a maintained, spec-compliant SDK already implements correctly — hand-rolling the wire protocol is exactly the kind of speculative, high-risk-of-subtle-bugs work YAGNI/KISS (§2.III) argue against for a security-sensitive integration boundary.

**Alternatives considered**: Hand-roll JSON-RPC 2.0 over `HttpClient` directly — rejected; reimplements a versioned protocol (including its Streamable HTTP/stdio framing edge cases) that this codebase has no prior experience shipping correctly, for no benefit over an existing SDK.

## Decision 3 — Namespaced tool identifier: zero schema change to `AgentTool`/`AgentToolCall`/`AgentPolicy`

**Decision**: Every discovered MCP tool's `McpTool.NamespacedName` is `mcp:{McpServerId}:{ToolName}` (a unique, indexed string column). This is the exact string agents reference via the *existing* `AgentTool.ToolName` column (spec 020's data-model.md — already a plain string, no FK to a `Tool` table) and the exact string an `AgentToolCall.ToolName`/`AgentPolicy.ToolName` records.

**Rationale**: Confirmed by direct inspection (`src/AskLucy.Persistence/Repositories/AgentPolicyRepository.cs`) that `AgentPolicy` matching is `WHERE p.ToolName == toolName` — exact string equality, no wildcard/prefix support. A namespaced string plugs into that comparison with zero code change: an administrator publishing an MCP-tool auto-approval policy (FR-026) uses the identical `CreateAgentPolicyCommand` UI/flow they already use for native tools, just targeting a `mcp:...` string. This also directly answers the endpoint-uniqueness/removal-blocking clarifications: "which agents reference server X" is `AgentTool` JOIN `McpTool` ON `AgentTool.ToolName == McpTool.NamespacedName` WHERE `McpTool.McpServerId == X` — no `LIKE` prefix scan needed.

**Alternatives considered**: A new `Tool`/`AgentToolReference` polymorphic table distinguishing native-vs-MCP at the schema level — rejected; spec 020's data-model.md explicitly chose "tools are code, not data" for native tools, and mirroring that decision (a plain string key, resolved against whichever catalog source currently owns it) is the smaller, more consistent change.

## Decision 4 — Tool activation gate: `McpToolActivationStatus`, independent of server-declared risk (clarification)

**Decision**: `McpTool` carries `ActivationStatus: PendingReview | Active | Deactivated`. Every tool starts `PendingReview` on first discovery. `IMcpToolRegistry.ActiveTools` (Decision 1) only ever includes tools that are simultaneously: `ActivationStatus == Active`, source `McpServer.IsEnabled == true`, and source server health is not `Unavailable`/`AuthenticationFailed`. An administrator's `ActivateMcpToolCommand`/`DeactivateMcpToolCommand` are the only way to move a tool into/out of `Active`.

**Rationale**: This is the clarification session's resolution — a compromised or misconfigured server cannot self-declare a dangerous tool "Low risk" and skip review, because risk classification and activation are two independent gates (FR-021/FR-022 handle classification; this decision handles activation) and *neither* alone makes a tool callable.

## Decision 5 — `AgentToolPermission` gains new values; `AgentToolRiskLevel` is unchanged

**Decision**: `AgentToolPermission` (`src/AskLucy.Application/Agents/Tools/IAgentTool.cs`) is extended with `ReadExternalData`, `WriteExternalData`, `SendCommunication`, `ModifyExternalSystem`, `DeleteExternalData`, `ExecuteOperation` — additive enum members, existing native-tool values (`ReadKnowledge`, `ReadMemory`, `ReadFile`, `WriteFile`, `ExternalNetwork`, `SendEmail`, `ExecuteCode`, `ModifyData`, `HighRiskOperation`) untouched. `AgentToolRiskLevel` (`Low | Medium | High | Critical`, Domain) needs no change — it already matches the spec's risk vocabulary verbatim.

**Rationale**: FR-021 requires mapping MCP-declared requirements onto "the platform's existing tool-permission vocabulary, extending that vocabulary only where an MCP tool's requirement has no existing equivalent." `DeleteExternalData` (e.g., deleting a record in a third-party system) has no honest equivalent among the native-tool-oriented values — `ModifyData` describes the platform's own data, not an external system's. Adding new enum members is additive (no migration risk to existing `AgentToolCall.RequiredPermissionsJson` rows, which store a JSON array of names, not ordinal values).

## Decision 6 — Approval, permission-checking, and duplicate-call detection are reused verbatim from the Agent Runtime

**Decision**: `McpToolAdapter : IAgentTool` (Decision 1) is a plain new `IAgentTool` implementation with no special-cased runtime path. The five runtime-enforced steps `contracts/agent-tool-contract.md` already documents for every tool (input validation, permission check, approval gate, output validation, duplicate-call detection) apply to it exactly as written — no new decision needed here beyond confirming the namespaced identifier (Decision 3) makes `AgentPolicy` matching, `AgentApproval` creation, and `AgentToolCall` recording all "just work" against an MCP tool the same as a native one.

**Rationale**: This is the literal mechanism by which FR-027/FR-028/FR-031 ("same permission validation, approval gating... same approval mechanism... unified timeline") are satisfied — by construction, not by parallel reimplementation.

## Decision 7 — Credentials: same ASP.NET Core Data Protection pattern as `AiCredentialProtector`

**Decision**: A new `IMcpCredentialProtector`/`McpCredentialProtector` pair, structurally identical to the existing `IAiCredentialProtector`/`AiCredentialProtector` (`src/AskLucy.Infrastructure/Ai/AiCredentialProtector.cs`), created from `IDataProtectionProvider.CreateProtector("AskLucy.McpServerCredentials")` (a distinct protector purpose string, so a key-ring compromise of one credential class doesn't automatically unlock the other). `McpServerCredential.CiphertextBlob` stores a single opaque encrypted string — for `ApiKey`/`BearerToken`, the raw value; for `OAuth2ClientCredentials`, a serialized `{clientId, clientSecret}` JSON blob — mirroring exactly how `AIProvider.CredentialCiphertext` already handles multiple credential shapes behind one column. `Application`/`Domain` never see plaintext; `McpServerCredential.SetCredential(ciphertext, actor)` accepts an already-encrypted string, same as `AIProvider.SetCredential`.

**Rationale**: This is the only credential-encryption mechanism this codebase has ever used (also backs `SignedUrlService` and `MemoryContentProtector`) — §2.VII requires following it rather than introducing a second (e.g., a KMS/Key Vault SDK dependency the codebase doesn't otherwise use). Directly satisfies FR-045/FR-046.

## Decision 8 — SSRF/endpoint validation is new infrastructure; validated at registration *and* at every connection

**Decision**: A new `IMcpEndpointValidator` (Application-owned interface) / `McpEndpointValidator` (Infrastructure) is built from scratch — confirmed by repo-wide search that no private-IP/loopback/link-local/cloud-metadata guard exists anywhere in this codebase today. It resolves the configured host via DNS and rejects the registration/connection if any resolved address falls in a private (`RFC1918`), loopback, link-local (`169.254.0.0/16`, includes the AWS/Azure/GCP metadata endpoint `169.254.169.254`), or otherwise non-routable range, unless `McpServer.EndpointValidationOverride` is explicitly set by an administrator (with a required justification string, itself audited via `McpAuditLog`). Validation runs both at registration time (FR-050) *and* again immediately before every connection attempt (health check, capability discovery, and every tool/resource/prompt call) — not just once at save time — to close a DNS-rebinding gap where a hostname resolves safely at registration but is repointed at an internal address later.

**Rationale**: This is a from-scratch build (no existing utility to reuse), which is why it gets its own decision and its own contract (`contracts/mcp-security-model.md`) rather than a one-line mention. Re-validating per-connection (not only at registration) is the standard SSRF/DNS-rebinding mitigation and is required to actually satisfy FR-050 against a server that changes its DNS answer after being allow-listed once.

## Decision 9 — JSON Schema validation is a new dependency (`JsonSchema.Net`); native tools are unaffected

**Decision**: `AskLucy.Infrastructure` (or `AskLucy.Application`, resolved at implementation time based on whether the validator needs to stay Infrastructure-free for testability — `JsonSchema.Net` has no I/O dependency, so it can live in `Application`) takes a new dependency on `JsonSchema.Net` to implement `IJsonSchemaValidator.Validate(schemaJson, instanceJson) : IReadOnlyList<string> errors`, used exclusively by `McpToolAdapter` to validate a discovered tool's arbitrary, externally-supplied `InputSchemaJson`/`OutputSchemaJson` against actual call data (FR-025/FR-026).

**Rationale**: Confirmed by inspecting every existing `IAgentTool` implementation (`FileReadTool.cs` et al.) that native tools do **not** use a generic JSON Schema validator — each hand-parses its own known, fixed shape (`input.RootElement.TryGetProperty("documentId", ...)`), and no `.csproj` in the solution references any JSON-Schema-validation package. That approach is infeasible for MCP: tool schemas are arbitrary and externally supplied by an untrusted party, so generic, spec-compliant validation is a genuine new requirement this feature introduces — not a gap in the existing pattern to imitate. `JsonSchema.Net` is chosen over `NJsonSchema` for its narrower scope (validation only, not C#-model code generation, which this use case doesn't need) and lack of transitive dependencies beyond `System.Text.Json`, already used everywhere in this codebase.

**Alternatives considered**: Hand-roll a minimal validator covering only `type`/`required`/`properties` — rejected; a security boundary (FR-025/FR-026, "reject malformed parameters") deserves a spec-compliant implementation, not a partial one that silently under-validates an edge case (e.g., `additionalProperties: false`, `enum`, numeric bounds) a malicious or buggy server could exploit.

## Decision 10 — Health checks and capability refresh are new Hangfire recurring jobs

**Decision**: Two new recurring jobs, registered exactly like `MemoryExtractionSweepJob`/`DocumentStatisticsRecomputeJob` (`RecurringJob.AddOrUpdate<T>(...)` in `Program.cs`, concrete class `services.AddScoped<T>()`'d in `DependencyInjection.cs`): `McpServerHealthCheckJob` (every 5 minutes — `PingAsync` every enabled server, updates `McpServerHealth`) and `McpCapabilityRefreshJob` (every 5 minutes — re-discovers capabilities for every server whose `LastCapabilityDiscoveryAt` is older than its own configurable `CapabilityRefreshIntervalMinutes`, default from `McpRuntimeOptions`). Both are also invokable synchronously via the "test connectivity"/"refresh now" admin actions (FR-008/FR-013), calling the same underlying Application-layer service the recurring job calls, not a duplicate code path.

**Rationale**: Hangfire recurring jobs are the codebase's only precedent for periodic background work — no `IHostedService` polling loop exists for anything comparable (research.md item confirming `ProviderHealthCheckHostedService` was 020's one exception, rejected there specifically because it doesn't survive a restart the way a Hangfire-scheduled job does; the same reasoning applies here for FR-055's "continuously... monitor" requirement surviving a deploy).

## Decision 11 — Outbound MCP calls use a named `IHttpClientFactory` client; retry/circuit-breaker is hand-rolled, not Polly

**Decision**: A new named client `"Mcp"` is registered in `DependencyInjection.cs` alongside the existing `"OpenAI"`/`"Anthropic"`/`"GoogleGemini"`/`"OpenRouter"` clients (same `IHttpClientFactory` pattern, no `BaseAddress` since it serves many different server endpoints, a bounded per-request timeout). Retry-with-backoff (FR-037's existing Agent Framework retry budget, reused conceptually) and a simple per-server circuit-breaker (open after N consecutive failures within a rolling window, half-open probe on the next health-check tick) are implemented as a small first-party `McpConnectionResiliencePolicy` class wrapping calls through `IMcpClient`, not a Polly pipeline.

**Rationale**: Repo-wide search confirms zero `Polly`/`AddPolicyHandler`/`CircuitBreaker` usage anywhere in `src` — introducing it here would be the first instance of a new resilience library for one feature, contradicting §2.VII (Convention over Configuration: extend what exists, don't introduce a parallel mechanism) when a small hand-rolled policy class fully covers this feature's stated needs (FR-037/FR-052/spec's Connection Management section) without a new dependency.

## Decision 12 — Two independent rate-limit layers: inbound REST (existing middleware) vs. outbound MCP calls (new in-process limiter)

**Decision**: (a) The new admin/user-facing REST controllers (Decision-driven contracts/mcp-api.md) get two new named ASP.NET Core rate-limiting policies — `mcp-admin-endpoints` and `mcp-endpoints` — registered in `Program.cs` exactly like the existing 11 policies (fixed-window, partitioned by user), applied via `[EnableRateLimiting("...")]`. (b) FR-052/FR-053's per-server/per-tool/per-user/per-agent limits on *outbound* MCP tool calls during agent execution are a **separate** concern — that traffic never passes through ASP.NET Core's request pipeline (it originates from the Hangfire execution runner) — so it is enforced by a new `IMcpRateLimiter`/`IMcpConcurrencyLimiter` built directly on `System.Threading.RateLimiting` primitives (`FixedWindowRateLimiter`/`ConcurrencyLimiter`). **Implementation correction**: this is a discrete NuGet package (`System.Threading.RateLimiting`), not an automatic transitive dependency — ASP.NET Core's `Microsoft.AspNetCore.RateLimiting` middleware ships inside the shared framework, not as a package `AskLucy.Infrastructure` pulls in. It is added as a small, first-party, version-locked (10.0.10, matching every other `Microsoft.Extensions.*` reference) third dependency alongside the two already recorded in Complexity Tracking (plan.md) — low-risk since it is a Microsoft-owned BCL-adjacent package, not a new third-party surface. Keyed by `(serverId, toolName, userId, agentId)` composite keys, checked by `McpToolAdapter.ExecuteAsync` before every call.

**Rationale**: Conflating these two would be a category error — one governs "how many times can this browser session hit `GET /api/v1/mcp/servers`," the other governs "how many concurrent calls is this agent execution allowed to make against this external server" — reusing the *primitives* (not the ASP.NET Core middleware itself) for the second case avoids a second bespoke rate-limiting implementation while respecting that it's a structurally different call site.

## Decision 13 — No new SignalR hub; admin health/discovery status is polled

**Decision**: The MCP Administration UI observes server health and capability-discovery status via ordinary TanStack Query polling (a short `refetchInterval`, matching every other admin list view in the codebase), not a new SignalR hub.

**Rationale**: Unlike spec 020's Agent Execution Hub (justified by SC-002's explicit "within 2 seconds" live-update requirement), this spec's equivalent success criterion (SC-006: "within one health-check cycle") is satisfied by the existing 5-minute recurring-job cadence (Decision 10) plus a poll — a fifth hub purely for admin dashboard freshness would be complexity §2.III (YAGNI) doesn't justify. Should a future spec need live push here, `IAgentExecutionNotifier`'s existing shape is the precedent to follow — no forward-compatibility work is needed to add it later.

## Decision 14 — Repository pattern mirrors `IAgentPolicyRepository`/`AgentPolicyRepository` exactly

**Decision**: `IMcpServerRepository`, `IMcpToolRepository`, `IMcpResourceRepository`, `IMcpPromptRepository`, `IMcpAuditLogRepository` (all `Application/Abstractions`, implemented in `Persistence/Repositories/Mcp/`) follow the confirmed existing shape: plain EF Core wrappers over `AskLucyDbContext` (primary-constructor classes), synchronous `Add`/no internal `SaveChanges` call (the caller's `IUnitOfWork.SaveChangesAsync` commits), aggregate-oriented query methods (no leaky `IQueryable` escape hatch, per constitution §3).

**Rationale**: Directly confirmed from `IAgentPolicyRepository.cs`/`AgentPolicyRepository.cs` — this is the established convention for a small aggregate in this exact feature area; no reason to deviate.

## Decision 15 — Server removal reference-blocking (clarification) via a repository join, not a LIKE scan

**Decision**: `IMcpServerRepository.CountReferencingAgentToolsAsync(serverId)` is implemented as `AgentTool` JOIN `McpTool` ON `AgentTool.ToolName == McpTool.NamespacedName` WHERE `McpTool.McpServerId == serverId` (both are indexed string columns per Decision 3) — `DeleteMcpServerCommand` rejects (422, listing the referencing `AgentId`/`ToolName` pairs) whenever this count is non-zero, satisfying FR-005/FR-065/the clarification's "block until references cleared."

**Rationale**: A `LIKE 'mcp:{serverId}:%'` prefix scan would work but bypasses the index-friendly equi-join Decision 3's namespaced-string design already enables; the join is both correct and the cheaper query plan.

## Decision 16 — MCP Prompts stay a separate, admin-scoped entity; "integration" means a unified picker plus a duplicate-to-native escape hatch

**Decision**: `McpPrompt` does **not** become a row in the existing `Prompt` table (`src/AskLucy.Domain/Prompts/Prompt.cs`, which is strictly `OwnerId`-scoped, per-user). Instead: (a) any UI/API surface that lets a user pick "a prompt" queries both `Prompt` (native, owned) and `McpPrompt` (shared, read-only, admin-registry-scoped) and returns a normalized DTO shape; (b) a new `DuplicateMcpPromptCommand` (mirroring the existing `DuplicatePromptCommand`, `src/AskLucy.Application/Prompts/Commands/DuplicatePrompt/`) creates a brand-new, fully independent, user-owned `Prompt` seeded from an `McpPrompt`'s current content — the read-only-mirror/duplicate-to-customize clarification's mechanism.

**Rationale**: Forcing `McpPrompt` into `Prompt`'s `OwnerId`-per-user model would misrepresent a shared, admin-managed resource as personal, private content, and would need `OwnerId` to mean something different for MCP-sourced rows than every other row in that table — a quiet special case FR-041's "integrate... rather than a second, disconnected prompt catalog" doesn't actually require. The existing `DuplicatePromptCommand` already proves the "take a copy, make it mine, edit freely" pattern this codebase uses elsewhere (also seen in `ImportPromptsCommandHandler`) — extending that pattern with one new source type is smaller than either forcing ownership semantics onto a shared resource or building prompt-level ACLs that don't exist anywhere else in the codebase.

## Decision 17 — Two-level failure categorization: coarse at the execution-history level, granular at the MCP-audit level

**Decision**: A failed MCP tool call still resolves to the *existing*, unchanged `AgentExecutionErrorCategory.ToolFailure` at the `AgentExecutionStep`/`AgentToolCall`/`AgentExecutionError` level (spec 020's enum, unmodified) — satisfying FR-032's "normalized into the platform's existing tool-failure/error handling... rather than a distinct MCP-specific failure path visible to the agent" literally. The finer-grained categories FR-033 requires (`ConnectionFailure` / `AuthenticationFailure` / `AuthorizationFailure` / `Timeout` / `RateLimit` / `InvalidRequest` / `InvalidResponse` / `ServerError` / `ProtocolError` / `CapabilityDiscoveryFailure` / `ServerUnavailable`, a new `McpFailureCategory` enum) are recorded only on `McpAuditLog`/`McpServerHealth` rows — the administrator-facing diagnostic surface, not the agent-facing execution history.

**Rationale**: These two requirements (FR-032 "don't leak MCP-specific failure shape to the agent/execution history" vs. FR-033 "record a specific failure category") would conflict if forced into one enum on one table; splitting them by *audience* (agent/user sees a uniform tool failure; administrator sees the granular diagnostic reason) satisfies both literally without contradiction.
