# Implementation Plan: Site Analysis Agent

**Branch**: `057-site-analysis-agent` | **Date**: 2026-09-17 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/057-site-analysis-agent/spec.md`

## Summary

Add a hierarchical agent that Lucy dispatches a site to. It resolves the site using the existing boundary
pipeline, then fans out to independent specialists through the existing workflow engine's `Parallel`/`Merge`
nodes. Each specialist reports to a parent relay the instant it finishes; the relay validates the result,
persists it, and only then delivers it — a chat notice plus a floating panel. Findings persist server-side so
they survive navigation and reload.

This release delivers the full coordination chain plus **one** specialist: a top-down schematic site map,
generated by OpenAI and persisted as a platform Document. Five further specialists are follow-up features and
must be addable as one provisioner entry plus one `IAgentTool` class.

The design is deliberately assembly rather than invention: the fan-out engine, background runner, panel push,
content vocabulary, boundary resolution, provider abstraction, and document pipeline all already exist and are
reused unchanged. See [research.md](./research.md) for the verified basis of each decision.

## Technical Context

**Language/Version**: C# / .NET 10 (backend), TypeScript 5 + React 19 (frontend)

**Primary Dependencies**: MediatR (CQRS), FluentValidation, EF Core, Hangfire (background execution), SignalR
(push), Serilog (structured logging), MUI, TanStack Query, Zustand, zod

**Storage**: SQL Server via EF Core code-first migrations; generated images via `IFileStorage` (local filesystem
today, cloud-swappable)

**Testing**: xUnit + NSubstitute (backend unit/integration), Vitest + Testing Library (frontend), axe (a11y)

**Target Platform**: ASP.NET Core web application, browser SPA client

**Project Type**: Web application — Clean Architecture backend (`Domain`/`Application`/`Infrastructure`/
`Persistence`/`Web`) plus a React SPA under `src/AskLucy.Web/ClientApp`

**Performance Goals**: Start acknowledgement returns within 3 s and always before the first finding (SC-001);
each finding reaches the user within 3 s of its specialist finishing (SC-002). Specialist execution itself is
bounded by existing workflow/agent execution limits, not by new budgets.

**Constraints**: Specialists run concurrently and MUST NOT be delivered as a batch; workflow branches are
limited to exactly one node each and must converge on a single Merge; findings must survive navigation/reload;
no invented figures where no data source exists.

**Scale/Scope**: Per-user, per-conversation analyses. This release: 1 specialist, ~6 new backend types plus one
aggregate, 1 new SignalR hub, 1 new client hook, 1 migration. Designed for 6 specialists total.

**Unknowns**: None outstanding. The pre-spec open item — which AI providers implement image generation — was
resolved by reading all four implementations (research D7): OpenAI only.

## Key Implementation Notes

These are the traps that will bite an implementer who has not read research.md:

1. **Do not deliver findings through workflow node notifications.** `ExecuteParallelAsync` batches them until
   every branch settles. Specialists call the relay inline. (research D3)
2. **Do not use `AiAgent` workflow nodes.** They cannot resolve system-owned agents and null out the chat link.
   (research D2)
3. **`RunByUserId` must be the real signed-in user**, never a system id — both notifiers are keyed by user id.
   (research D12)
4. **Never hand the provider's image URL to the client.** Persist via `DocumentUploadFinalizer` and pass a
   `fileId`; the block schema rejects external URLs anyway. (research D8)
5. **Use the `AnyCompleted` merge strategy**, or one failed specialist fails the whole analysis. (research D13)
6. **Never derive confidence from geocoding `Importance`** — the two providers populate it on incompatible
   scales. (research D10)
7. **Mirror the provisioner's defer-on-pending-migrations behavior**, or a fresh database breaks startup.
   (research D12)

## Complexity Tracking

| Violation | Why Needed | Simpler Alternative Rejected Because |
|-----------|------------|-------------------------------------|
| Dispatcher bypasses `StartWorkflowExecutionCommand` and constructs `WorkflowExecution` directly, rather than going through the CQRS command surface (§3) | The command's `WorkflowOwnershipGuard.EnsureOwnedBy` hard-checks `OwnerId == userId`. A single shared, system-owned workflow triggered by any signed-in user can never satisfy it. | Relaxing the guard to permit system-owned workflows would weaken an authorization control on the *user-facing* workflow surface to serve an internal caller — rejected under §8 ("never weaken a security control to make a feature work") and §18. Giving every user their own copy of the workflow was rejected as unmanageable drift. This mirrors the established precedent that conversation capabilities call services directly rather than through CQRS. |
| Three data-provider interfaces ship with no implementation (§2 III YAGNI) | FR-014 is a current requirement: specialists must report a named reason when a figure has no data source. That contract must exist for the deferred specialists to be addable without structural change (FR-031). | Omitting them would force the first follow-up specialist to invent both the seam and its outcome vocabulary mid-feature, or — worse — to present inferred figures as measured, which FR-014 forbids. Scope is held to the interface and its outcome type only: no DTOs, configuration, or partial implementations. |

**No ADR required.** Neither entry introduces a new datastore, a new cross-cutting pattern, nor an
expensive-to-reverse decision (§17) — the first follows an existing precedent in the codebase, and the second is
three interface declarations.
