# Feature Specification: Multi-Provider AI Engine

**Feature Branch**: `005-multi-provider-ai-engine`

**Created**: 2026-07-30

**Status**: Draft

**Input**: User description: "Transform Ask Lucy from an application tied to a single AI provider into a provider-agnostic AI platform capable of communicating with multiple Large Language Model (LLM) providers through a unified abstraction layer. Allow users to configure providers, select models, customize generation parameters, and seamlessly switch between providers without changing application code. Support OpenAI, Anthropic, Google Gemini, and OpenRouter initially, with the architecture able to add future providers by implementing interfaces rather than modifying existing business logic. Excludes RAG, AI Agents, MCP, Prompt Library, User Memory, and Team Workspaces."

## Clarifications

### Session 2026-07-30

- Q: The constitution requires AI-invoking endpoints to enforce token/cost-based throttling, not just request-count throttling. Should this spec include a requirement for per-user/tenant AI request throttling, or defer it? → A: No new requirement in this spec — baseline request-count rate limiting is a platform-wide default already covered elsewhere; token/cost-based throttling is deferred to the future Billing Engine spec.
- Q: Can a model marked "deprecated" still be selected for a brand-new conversation, or is it functionally the same as "unavailable"? → A: Deprecated models are immediately unselectable for new use, functionally identical to "unavailable"; the status is only a label for admin reporting.
- Q: What should a user see if they open chat while zero AI providers are enabled (distinct from a provider failing mid-use, already covered by FR-029)? → A: Out of scope for this spec — assume production deployments always have at least one provider enabled before end users get access; no dedicated empty-state UI is required.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Administrator enables providers and configures credentials (Priority: P1)

An administrator turns on one or more AI providers for the platform and supplies the credentials each provider needs, so that users have at least one working AI provider to chat with.

**Why this priority**: Nothing else in this feature can be demonstrated or tested until at least one provider is enabled and reachable. This is the enabling foundation for every other story.

**Independent Test**: Can be fully tested by an administrator enabling a provider, entering a credential, and confirming the provider reports a healthy status — independent of any end-user chat flow.

**Acceptance Scenarios**:

1. **Given** a provider is currently disabled, **When** an administrator enables it and supplies a valid credential, **Then** the provider becomes available for users to select and its status shows healthy.
2. **Given** an administrator enters an invalid or malformed credential, **When** they save it, **Then** the system rejects the save with a clear validation error and the provider remains disabled.
3. **Given** a provider is enabled, **When** an administrator disables it, **Then** it immediately stops appearing as a selectable option for users starting new messages.
4. **Given** a credential was saved previously, **When** an administrator or any other user views the provider configuration afterward, **Then** the credential value itself is never displayed in plain text.

---

### User Story 2 - User chats using a chosen provider and model (Priority: P1)

A user picks an AI provider and a model from that provider, sends a message, and can see which provider and model produced each response in the conversation.

**Why this priority**: This is the core value of the feature — proof that the platform can hold a real conversation through more than one vendor, and that users understand what generated each reply.

**Independent Test**: Can be fully tested by starting a new conversation, selecting a specific provider/model combination, sending a message, and verifying the reply is labeled with that exact provider and model.

**Acceptance Scenarios**:

1. **Given** two or more providers are enabled, **When** a user starts a new conversation, **Then** they can choose any enabled provider and any of its available models before sending their first message.
2. **Given** a user sends a message, **When** the response arrives, **Then** the message is visibly labeled with the provider and model that generated it, and that label persists for the life of the conversation.
3. **Given** an ongoing conversation, **When** the user switches to a different enabled provider/model and sends another message, **Then** the new response is generated by the newly selected provider/model while every earlier message keeps the attribution it already had.
4. **Given** a provider is disabled by an administrator, **When** a user opens the provider/model picker, **Then** the disabled provider does not appear as a selectable option.
5. **Given** streaming is supported by the selected model, **When** a response is generated, **Then** the reply appears incrementally as it is produced rather than only after the full response completes, with the same on-screen behavior regardless of which provider is selected.

---

### User Story 3 - User sets default provider/model preferences (Priority: P2)

A user sets a personal default AI provider and model in their settings so that every new conversation starts pre-configured the way they prefer, without having to choose every time.

**Why this priority**: Removes repetitive setup friction once the core multi-provider chat (Story 2) works, materially improving day-to-day usability.

**Independent Test**: Can be fully tested by setting a default provider/model in settings, starting a brand-new conversation, and confirming it opens pre-selected with that provider/model.

**Acceptance Scenarios**:

1. **Given** a user has not yet set a default, **When** they start their first conversation, **Then** the system pre-selects a sensible default (e.g., the platform's designated default provider/model).
2. **Given** a user changes their default provider/model in settings, **When** they start a new conversation afterward, **Then** it opens pre-configured with the new default; conversations already in progress are unaffected.
3. **Given** a user's saved default provider is later disabled by an administrator, **When** the user next starts a new conversation, **Then** the system falls back to another enabled provider/model and clearly indicates the change, rather than failing silently.

---

### User Story 4 - User configures generation parameters (Priority: P2)

A user adjusts generation parameters (such as temperature, response length, streaming, and system prompt) for a conversation so the AI's behavior better fits their task.

**Why this priority**: Builds directly on Story 2's chat experience and is high-value for power users, but the platform is usable without it.

**Independent Test**: Can be fully tested by opening the parameter panel for a conversation, changing a parameter, sending a message, and confirming the response reflects the new setting (e.g., a very low temperature produces a more deterministic reply than a very high one).

**Acceptance Scenarios**:

1. **Given** a user opens the generation parameter panel, **When** they adjust a supported parameter and save, **Then** subsequent responses in that conversation are generated using the updated value.
2. **Given** a user enters a parameter value outside the allowed range, **When** they attempt to save it, **Then** the system rejects the value with an inline explanation of the valid range.
3. **Given** a selected model does not support a given parameter (e.g., a reasoning-level setting on a model without reasoning support), **When** the user views the parameter panel, **Then** the unsupported control is hidden or clearly disabled rather than silently ignored.

---

### User Story 5 - User sees token usage and estimated cost (Priority: P3)

A user views the token usage and estimated cost for each AI response and for the conversation overall, so they understand what their usage is costing.

**Why this priority**: Adds transparency and trust on top of an already-working chat experience; valuable but not blocking for a functional MVP.

**Independent Test**: Can be fully tested by sending a message and confirming the resulting message displays input/output token counts and an estimated cost, matching the provider and model that generated it.

**Acceptance Scenarios**:

1. **Given** a response has been generated, **When** a user views that message, **Then** they can see its input token count, output token count, and an estimated cost.
2. **Given** a conversation has multiple messages across different providers/models, **When** a user views a usage summary for the conversation, **Then** totals are correctly attributed and aggregated per provider and model.
3. **Given** a provider does not report token usage for a given call, **When** the response is displayed, **Then** the system clearly indicates usage/cost is unavailable rather than showing a fabricated or blank value.

---

### User Story 6 - Administrator monitors provider health and usage (Priority: P3)

An administrator views the health status, usage, and cost of each configured provider so they can react to outages or unexpected spending.

**Why this priority**: Operational visibility that matters once providers are live in production, but is not required to prove the core feature works.

**Independent Test**: Can be fully tested by simulating a provider becoming unreachable and confirming the administrator's provider health view reflects the degraded/unhealthy status, independent of any end-user action.

**Acceptance Scenarios**:

1. **Given** an enabled provider stops responding successfully, **When** the next scheduled health check runs, **Then** the administrator's view shows that provider as unhealthy along with when it was last checked.
2. **Given** a provider recovers, **When** the next health check succeeds, **Then** its status returns to healthy without requiring manual administrator intervention.
3. **Given** a reporting period, **When** an administrator views usage statistics, **Then** they can see aggregated request counts, token usage, and estimated cost broken down by provider and model.

---

### User Story 7 - User compares responses from multiple models (Priority: P4)

A user sends the same prompt to two or more models at once and views the responses side by side to decide which best fits their task.

**Why this priority**: A valuable differentiator once the platform reliably supports single-provider chat, defaults, and parameters, but it is the most complex story and least essential to core value.

**Independent Test**: Can be fully tested by selecting two or more models for a single prompt and confirming the response view shows each model's reply clearly attributed and lets the user pick one to continue the conversation from.

**Acceptance Scenarios**:

1. **Given** a user selects two or more enabled provider/model combinations for a comparison, **When** they submit a single prompt, **Then** each selected model's response is displayed side by side, each clearly labeled with its provider and model.
2. **Given** a comparison has completed, **When** the user selects one of the responses to continue from, **Then** the conversation continues using that response's provider/model, and the other comparison responses remain visible in history but are not used as further context.
3. **Given** one of the selected models fails to respond (error or timeout), **When** the comparison results are shown, **Then** the failed model's slot clearly shows an error state while the other models' responses are still displayed.

---

### Edge Cases

- What happens when all enabled providers become unreachable at the same time? System must surface a clear, user-visible failure state rather than an unhandled error or a silently stuck "thinking" indicator.
- What happens when a user has an in-flight streaming response and switches provider/model before it finishes? The in-flight response must complete or be cleanly cancelled before the new selection takes effect; it must not be silently discarded without explanation.
- What happens when an administrator removes/deprecates a model that is referenced by existing conversation history? Historical messages must continue to display which model actually generated them, even after that model is no longer selectable for new messages.
- What happens when a provider partially fails mid-stream (connection drops after some tokens were already sent)? The partial response must be preserved and clearly marked as incomplete/interrupted, not discarded and not presented as a complete answer.
- What happens when a user sets generation parameters that conflict with a model's declared capabilities (e.g., requesting JSON mode from a model that doesn't support it)? The system must prevent the conflicting request or clearly explain why the parameter was not applied, not silently ignore it.
- What happens when estimated cost cannot be computed because pricing metadata for a model is missing? The system must show usage as unavailable rather than a misleading value such as zero.
- What happens when a provider's credential expires or is revoked externally, mid-use? Requests must fail gracefully with a clear, actionable error rather than a generic failure, and the provider's health status must reflect the problem.
- How does the system handle a user selecting a model comparison (Story 7) where one of the chosen models belongs to a provider that becomes disabled between selection and submission? The disabled provider's model must be excluded from the run with a clear explanation, rather than silently failing the whole comparison.

## Requirements *(mandatory)*

### Functional Requirements

**Provider & model configuration**

- **FR-001**: System MUST support at least the following AI providers: OpenAI, Anthropic, Google Gemini, and OpenRouter.
- **FR-002**: System MUST allow a new AI provider to be added to the platform without requiring changes to existing conversations, existing provider integrations, or any other previously working functionality.
- **FR-003**: System MUST allow administrators to enable or disable each provider independently.
- **FR-004**: System MUST allow administrators to configure and rotate provider credentials, and MUST never display a stored credential in plain text after it has been saved.
- **FR-005**: System MUST maintain a catalog of models available per provider, including at minimum: name, display name, context window size, maximum output tokens, and which capabilities it supports (streaming, vision, function calling, JSON mode, reasoning, embeddings, image input/output, audio).
- **FR-006**: System MUST allow administrators to mark individual models as available, deprecated, or unavailable, independently of the provider's own status. Deprecated and unavailable both remove a model from user selection (see FR-007) and differ only in administrative meaning: deprecated indicates a planned phase-out (kept for reporting/audit), unavailable indicates it is currently non-functional or intentionally disabled.
- **FR-007**: Users MUST only be able to select providers and models that are currently enabled and marked available; disabled providers and any model marked deprecated or unavailable MUST NOT appear as selectable options anywhere in the product, for new or ongoing conversations alike.

**Chat experience**

- **FR-008**: Users MUST be able to choose a provider and a model for a conversation before sending a message.
- **FR-009**: Users MUST be able to change the provider and/or model for an ongoing conversation, with the change applying to subsequent messages only.
- **FR-010**: System MUST permanently record, for every message, the exact provider and model that generated it, and MUST display that attribution to the user.
- **FR-011**: System MUST preserve each historical message's original provider/model attribution even after that provider or model is later disabled, deprecated, or removed from selectable options.
- **FR-012**: System MUST support streaming responses, and the on-screen streaming behavior MUST be identical from the user's perspective regardless of which provider generated the response.
- **FR-013**: System MUST allow a user to cancel an in-progress response.

**Generation parameters**

- **FR-014**: Users MUST be able to configure generation parameters including temperature, top P, top K, presence penalty, frequency penalty, maximum response length, stop sequences, seed, reasoning level, response format/JSON mode, streaming on/off, and system prompt.
- **FR-015**: System MUST only expose a given generation parameter for a conversation when the currently selected model supports it, and MUST prevent submitting a request that combines a parameter with a model that doesn't support it.
- **FR-016**: System MUST validate generation parameter values against each parameter's allowed range/format before applying them, and MUST reject invalid values with a clear, specific explanation.

**Preferences & defaults**

- **FR-017**: Users MUST be able to set a personal default provider and model, applied automatically to new conversations.
- **FR-018**: System MUST fall back to another enabled provider/model, with a clear on-screen notice, when a user's saved default becomes unavailable.
- **FR-019**: Users MUST be able to save default generation parameter values (e.g., preferred temperature, streaming preference, system prompt) that apply to new conversations.

**Usage & cost**

- **FR-020**: System MUST record, per message, input tokens, output tokens, cached tokens and reasoning tokens (when the provider reports them), latency, provider, model, and estimated cost.
- **FR-021**: System MUST display token usage and estimated cost to the user for each AI response and as an aggregate for the conversation.
- **FR-022**: System MUST maintain pricing metadata per model sufficient to compute an estimated cost, and MUST clearly indicate when usage/cost cannot be determined rather than showing a fabricated value.
- **FR-023**: System MUST make token usage and cost data available to administrators in aggregate, broken down by provider and model, for a given reporting period.

**Model comparison**

- **FR-024**: Users MUST be able to submit a single prompt to two or more enabled provider/model combinations at once and view the responses side by side, each clearly labeled with its provider and model.
- **FR-025**: Users MUST be able to select one comparison response to continue the conversation from; the other comparison responses MUST remain visible in history but MUST NOT be used as further context.
- **FR-026**: When one model in a comparison fails to respond, System MUST show that failure clearly for the affected model while still returning results from the models that succeeded.

**Provider health & reliability**

- **FR-027**: System MUST periodically check the health of each enabled provider and make the current health status visible to administrators, including the time of the last check.
- **FR-028**: System MUST translate provider-specific error conditions (rate limits, authentication failures, timeouts, service outages) into a consistent set of user-facing error messages, regardless of which provider produced the error.
- **FR-029**: When a provider is unreachable or fails, System MUST surface a clear, visible failure to the user — including a way to retry or switch provider — and MUST NOT leave the conversation in a silent or indefinitely "loading" state.
- **FR-030**: When a streaming response is interrupted mid-generation, System MUST preserve and clearly mark the partial response as incomplete rather than discarding it or presenting it as complete.

**Security**

- **FR-031**: System MUST restrict provider credential configuration to administrators only; non-administrator users MUST NOT be able to view, set, or export provider credentials through any part of the product.
- **FR-032**: System MUST NOT expose which provider/model a request will use to any party besides the requesting user and system administrators until the response is returned (no cross-user leakage of in-flight provider/model selection).
- **FR-033**: AI chat request endpoints introduced by this feature MUST be covered by the platform's existing baseline per-user/tenant request-count rate limiting; this feature does not introduce additional token- or cost-based throttling (see Clarifications, Assumptions).

### Key Entities

- **AI Provider**: A vendor/service the platform can send AI requests to (e.g., OpenAI, Anthropic, Google Gemini, OpenRouter). Tracks whether it is enabled, its current health status, and its associated credential.
- **AI Model**: A specific model offered by a provider (e.g., a particular chat model). Tracks its display name, context window, output limits, supported capabilities, status (available/deprecated/unavailable), and release information.
- **Provider Configuration**: The administrator-managed settings for a provider, including its credential reference, enabled/disabled state, and default model.
- **Conversation Model Settings**: The provider, model, and generation parameters associated with a conversation (and, per message, the exact provider/model used to generate that message).
- **Message Usage**: The recorded token counts (input, output, cached, reasoning), latency, provider, model, and estimated cost for a single AI response.
- **Provider Health Record**: A timestamped record of a provider's health-check outcome, used to show current and historical availability.
- **Model Pricing**: Pricing metadata for a model (e.g., cost per input/output token) used to compute estimated cost.
- **User AI Preferences**: A user's personal default provider, default model, and default generation parameters, applied to new conversations.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A user can start a new conversation, select any enabled provider and model, and receive a labeled response in under 10 seconds of the model's own response time (excluding model "thinking" time itself).
- **SC-002**: 100% of stored messages display the exact provider and model that generated them, verifiable at any point after the fact, including for messages whose original provider/model has since been disabled or deprecated.
- **SC-003**: A new AI provider can be made available to users by an administrator configuring it through settings alone, with zero changes required to any existing conversation, provider, or feature already in production.
- **SC-004**: When an enabled provider becomes unreachable, 100% of affected in-progress requests result in a clear, visible error or fallback to the user — none are left in an indefinite loading state or fail with no visible outcome.
- **SC-005**: Estimated cost shown to users is available for at least 95% of responses generated by providers that report token usage.
- **SC-006**: An administrator can detect a provider outage (health status change from healthy to unhealthy) within one health-check interval of it occurring, without needing to be told by a user.
- **SC-007**: 90% of users testing the default-provider and parameter-configuration settings can locate and change their default provider/model on their first attempt without external help.
- **SC-008**: In a side-by-side comparison of 2+ models, 100% of successfully-responding models display their result; a failure in one model never blocks or hides the results of the others.

## Assumptions

- **Existing single-provider constraint is superseded.** The current codebase has a single hardcoded provider abstraction with an explicit prior constraint forbidding additional providers or model switching. This specification supersedes that constraint; reconciling the existing abstraction with the new multi-provider requirements is a planning/implementation concern, not a scope question for this spec.
- **Access is not gated by subscription tier in this spec.** All authenticated users may select any provider/model an administrator has enabled; tier-based access restrictions are deferred to a future Billing Engine specification, consistent with this feature explicitly excluding billing implementation.
- **Cost estimation is informational only.** This specification does not include enforcement of spending caps, quotas, or automatic blocking based on usage/cost — only visibility. Enforcement is deferred to a future Billing Engine specification.
- **AI request rate limiting is not newly introduced by this spec.** (Resolved 2026-07-30, see Clarifications.) Baseline per-user/tenant request-count rate limiting is a platform-wide default that already applies to this feature's endpoints; token/cost-based throttling for AI-invoking endpoints is deferred to the future Billing Engine specification, consistent with the cost-estimation assumption above.
- **Model catalog is administrator-curated.** Available models come from an internal, administrator-maintained registry (which may be informed by a provider's own model-discovery capability) rather than being fetched live from each provider on every request, consistent with the caching/performance expectations for this feature.
- **A platform-wide default provider/model exists.** Until a user sets a personal default, the system falls back to a platform-configured default so a first-time user is never left without a usable starting point.
- **A zero-providers-enabled state is out of scope.** (Resolved 2026-07-30, see Clarifications.) Production deployments are assumed to always have at least one provider enabled before end users get access; this spec does not define a dedicated "no providers configured" empty state for the chat UI.
- **Health checks run on a recurring schedule** rather than being triggered per-request, to avoid adding latency to user-facing chat requests.
- **RAG, AI Agents, MCP tool orchestration, Prompt Library, User Memory, and Team Workspaces are explicitly out of scope**, as stated in the input, and this feature's model/provider abstraction is expected to be reused — not redesigned — when those future specifications are implemented.
- **Image generation, speech-to-text, text-to-speech, and embeddings are out of scope for this spec's user-facing functionality** beyond being represented as model capability flags in the catalog (FR-005); wiring those modalities into end-to-end product features is left to their own future specifications, consistent with the objective's exclusion list.
