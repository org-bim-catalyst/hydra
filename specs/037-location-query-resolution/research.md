# Research: Location Query Resolution

**Branch**: `037-location-query-resolution` | **Date**: 2026-08-23

---

## Decision 1 — Concurrent Resolution + Deterministic Confirmation Text, Not Model-Native Tool-Calling

**Decision**: Location intent classification and geocoding run as a single background `Task<LocationResolutionOutcome>` launched at the same point `SendChatMessageCommandHandler` currently kicks off `aiProvider.StreamChatAsync` — i.e., concurrently with the model's own generation, never before it. After the content-delta loop finishes, the handler awaits that task with a deadline equal to whatever remains of the 15 s ceiling (FR-013), then — for any outcome except `NoIntent` — yields one additional `ChatStreamChunk` whose `ContentDelta` is a **deterministic, template-based** sentence (`LocationConfirmationTemplates`), not text generated by the LLM itself. `ConfirmedLocationData` rides the existing trailing chunk exactly as specs 035/036 already defined it.

**Rationale**: `IAIProvider` (`src/AskLucy.Application/Abstractions/IAIProvider.cs`) has no tool-calling/function-calling surface at all for the regular chat pipeline — `StreamChatAsync` yields plain `string`/`StreamChunk` content deltas, nothing a provider could pause on to receive a mid-generation result. Real tool-calling only exists in the separate, heavyweight Agent Runtime (`IAgentTool`/`AgentToolCatalog`, specs 020/021) used by user-authored autonomous agents — adding that machinery to the core Chat Engine's `SendChatMessageCommandHandler` for one feature would be a large, out-of-scope architectural change. Given that constraint, there is no way for the model's own streamed tokens to accurately narrate a geocoding result that wasn't ready when generation started. Two designs were possible:
- **(A) Pre-generation, blocking** — classify + geocode before building the message list (exactly how RAG/Memory retrieval already work in this same handler), inject the outcome as a system message, let the model narrate it naturally. Rejected: this makes every location-bearing turn wait out the full classification+geocoding round trip before *any* text appears, which is what spec FR-008 explicitly forbids, and it makes FR-013's clarified wording — "when Lucy's text reply finishes streaming *before* geocoding completes" — unsatisfiable (under this design geocoding always finishes before text starts, so that clause could never fire).
- **(B) Concurrent, deterministic append** — chosen. Generation starts immediately (FR-008 satisfied exactly); the resolution task races it; whatever isn't done by the time text finishes gets the remaining time (FR-013 as clarified). The trade-off is that the confirmation/failure sentence is a fixed template rather than the model's own free-form phrasing — an acceptable cost since the *viewer* update (the real payload) is unaffected either way, and the template still arrives as an ordinary part of the same streamed response the user is already reading, satisfying User Story 1 AC1 ("Lucy's streamed reply confirms the resolved place name").

**Alternatives considered**:
- Pre-generation blocking classification+geocode (Design A above) — rejected per FR-008/FR-013 conflict, detailed above.
- Adding real tool-calling to `IAIProvider` across all four providers — rejected: far beyond this feature's scope, no other call site needs it yet, and it would need its own spec/plan.
- Racing geocoding but silently dropping the confirmation when it doesn't beat the model's own text (no deterministic append at all) — rejected: violates FR-005/User Story 3 (no silent no-op) and User Story 1 AC1 (the reply must confirm the place name in words the user can read).

## Decision 2 — Location Resolution as an `Application`-Layer Pipeline Service, Mirroring `IRagService`/`IMemoryService`

**Decision**: Introduce `ILocationResolutionService.ResolveAsync(userId, userChatId, latestUserMessage, activeLocation, cancellationToken) → LocationResolutionOutcome`, implemented by `LocationResolutionService` in `AskLucy.Application/Locations/`, registered in `AskLucy.Application/DependencyInjection.cs` exactly where `IRagService`/`IMemoryService` are registered today. Called from `SendChatMessageCommandHandler` at the same point RAG/Memory are called (`request.Messages[^1].Content` as the query), but its `Task` is stored and awaited later rather than awaited inline (Decision 1).

**Rationale**: This is the third "does this turn need extra context/action beyond raw generation" pipeline stage in this handler, after RAG and Memory. Both existing ones share a contract this feature should match rather than reinvent: never throw for a retrieval/processing-time failure (return a typed `Unavailable`-style outcome instead — constitution §2.VIII), and ride the final `ChatStreamChunk` so a subsystem outage degrades gracefully rather than blocking the turn. `SendChatMessageCommandHandler` must also stay unit-testable with all dependencies faked (§2.V) — an interface seam here lets `SendChatMessageCommandHandlerTests` fake location resolution exactly like it already fakes `IRagService`/`IMemoryService`, without needing to fake `IAIProvider` and a geocoding HTTP client both.

**Alternatives considered**:
- Inline the classification/geocoding logic directly in the handler — rejected: the handler already orchestrates three concerns (RAG, Memory, generation); a fourth inline concern would violate SRP (§2.II) and make the handler untestable without live HTTP/LLM calls.
- Model it as an `IAgentTool` invoked through `AgentToolCatalog` — rejected: that catalog is the Agent Runtime's tool-calling surface (specs 020/021), which regular chat turns don't go through at all (confirmed: `SendChatMessageCommandHandler` has zero references to `IAgentTool`/`AgentToolCatalog`). Using it here would require wiring the heavyweight approval-gate/permission-check runtime into a code path that was never designed to carry it.

## Decision 3 — Intent Classification via a Structured LLM Call on the Default Provider, Not Regex/Keyword Heuristics

**Decision**: `LocationResolutionService` classifies the latest user message with one non-streaming `IAIProvider.ChatAsync(...)` call, resolved via the existing `DefaultProviderResolver` (the same dependency `MemoryExtractionJob`/`MemoryConflictDetectionService` already use for background classification/extraction calls — not the user's turn-selected provider/model). The system prompt (versioned as `LocationIntentClassificationPromptV1`, per constitution §9's "prompt engineering... versioned artifacts") instructs the model to return strict JSON: `{"intent":"none"|"new_query"|"back_reference","placeQueries":["..."]}`. The response is parsed with `JsonSerializer.Deserialize`, exactly like `MemoryExtractionJob.ParseCandidates`.

**Rationale**: User Story 2's core requirement — distinguishing "show me Al Safa Park 2" (navigational intent) from "I read that Al Safa Park was renovated" (passing mention) — is a semantic judgment call that a keyword/regex heuristic cannot reliably make (both sentences contain the same place name; only the surrounding verbs and framing differ, in ways that vary by phrasing and language). This is exactly the kind of judgment the existing `MemoryExtractionJob`/`MemoryConflictDetectionService` precedent already delegates to a small LLM call with a strict JSON contract, rather than to string matching. Reusing `DefaultProviderResolver` (rather than the turn's own selected provider/model) keeps classification latency and behavior independent of whatever model the user happens to have picked for their main conversation, and avoids threading `aiProvider`/`model` into `ILocationResolutionService`'s signature.

**Alternatives considered**:
- Regex/keyword heuristic ("show me", "where is", "take me to", etc.) — rejected: brittle against phrasing variation and the exact false-positive/false-negative cases spec's Edge Cases call out; would require constant tuning as new phrasings are discovered in production.
- Reuse the turn's own selected provider/model for classification — rejected: couples an internal pipeline concern to a user-facing choice meant for generation quality/cost trade-offs, not classification; also would require passing `aiProvider`/`model` through the service's public contract, contradicting Decision 2's goal of a minimal call-site shape matching `IRagService`/`IMemoryService`.
- Ask the primary generation call itself to emit an inline marker (e.g. `[[LOCATION: ...]]`) inside its own streamed text, parsed out by the controller — rejected: requires the model to have already decided the outcome before generating (same blocking problem as Decision 1's Design A), and silently mixing control syntax into free-form text is fragile to parse reliably (a stray bracket in the model's own prose could misfire).

## Decision 4 — Geocoding via the Existing Nominatim Host, Not a New Provider

**Decision**: Forward geocoding (place name → coordinates) reuses the same Nominatim deployment already wired for weather's reverse-geocoding (`WeatherProvider.ResolveLocationNameAsync`, `nominatim.openstreetmap.org`), via Nominatim's `/search` endpoint. A new `IGeocodingProvider` (`SearchAsync(query, cancellationToken) → IReadOnlyList<GeocodingCandidate>`) is implemented by `NominatimGeocodingProvider` in `AskLucy.Infrastructure/Geocoding/`, reusing the existing "Weather" named `HttpClient` registration (`services.AddHttpClient("Weather", ...)` in `Infrastructure/DependencyInjection.cs`) and the same descriptive `User-Agent` header Nominatim's usage policy requires (`AskLucy/1.0 (+https://hydra.bimcatalyst.com)`), rather than registering a second named client for the same host.

**Rationale**: This directly satisfies spec 037's Assumption ("the geocoding/geospatial data source... as already assumed in spec 035 — an openly available service such as OpenStreetMap Nominatim or equivalent") and constitution §7's Convention over Configuration — the host, timeout budget (15 s, already configured on the "Weather" client and numerically identical to FR-013's ceiling), and keyless/no-secret-to-protect posture are all already established and proven in production by `WeatherProvider`. A new `GeocodingOptions.SearchBaseUrl` (defaulting to the same host as `WeatherOptions.ReverseGeocodingBaseUrl`) is introduced rather than reusing `WeatherOptions` directly, keeping the two capabilities independently configurable (constitution §9-equivalent provider-swap principle: forward geocoding could move to a paid provider later without touching weather) while still defaulting to the same free host today.

**Alternatives considered**:
- A different geocoding provider (Google/Mapbox/HERE) — rejected: would require a new API key (constitution §8 secret custody + cost), where Nominatim's existing keyless deployment already meets the need and is already proven in this codebase.
- Reusing `WeatherOptions`/`IWeatherProvider` directly for forward search — rejected: conflates two distinct capabilities (weather lookup vs. place search) behind one interface, violating ISP (§2.II); a future provider swap for one would force touching the other.
- A second, separately named `HttpClient` for the same host — rejected: no configuration actually differs (same host family, same 15 s timeout is exactly what FR-013 wants), so a second registration would be pure duplication with no behavioral benefit.

## Decision 5 — Confidence Algorithm: Dominant-Result Margin Over Nominatim's Raw `importance`

**Decision**: After calling `/search?q={query}&format=json&addressdetails=1&limit=5`, results with `importance` below a floor (`MinimumImportanceFloor = 0.1`, filtering obvious noise matches) are discarded. Of what remains:
- **Zero results** → `NotFound`.
- **One result** → `Confirmed`, with `Confidence` set to that result's `importance` (Nominatim's own 0–1 relevance score, already present in every `/search` response).
- **Two or more results** → compare the top two by `importance`. If the leader exceeds the runner-up by at least `DominanceMargin = 0.2`, treat the leader as a `Confirmed` single match (its own importance as `Confidence`); otherwise `Ambiguous`.

**Rationale**: Nominatim's raw `importance` is a Wikipedia-page-rank-style popularity score, not a "does this match the query" confidence — a legitimate, unambiguous match for a moderately-known place (e.g. a named neighborhood park) can score low in absolute terms while still being the only real candidate. Requiring a high absolute `importance` would produce false `NotFound`/`Ambiguous` outcomes for exactly the kind of specific, correctly-spelled query spec's User Story 1 exists to handle. Comparing the *margin* between the top two results instead answers the question spec's User Story 3 actually cares about — "is there a clearly dominant single answer, or does the query genuinely have competing candidates" — which is what separates a confident single match from a real ambiguity (e.g. "Springfield," which returns many similarly-scored state capitals with no dominant leader).

**Alternatives considered**:
- Top-1-result-always-wins (ignore `importance` entirely) — rejected: would silently auto-confirm on the historically-first/nearest Nominatim result even for genuinely ambiguous multi-city names, directly violating FR-005/User Story 3's "never guess" requirement.
- Absolute `importance` threshold only (e.g. "confident iff importance ≥ 0.5") — rejected: as explained above, legitimate specific-place queries often score below any reasonable absolute floor, which would make the feature fail on exactly its headline example ("Al Safa 2 Park").
- A fixed maximum candidate count from Nominatim (e.g. `limit=1`) instead of comparing several — rejected: makes ambiguity detection (FR-005/FR-009) impossible, since the service would never see that other, comparably-relevant candidates existed.

## Decision 6 — Back-Reference State: A Minimal `ActiveSiteLocation` Owned Type on `UserChat`

**Decision**: `UserChat` gains a nullable EF Core owned-type property `ActiveLocation` of a new value object `ActiveSiteLocation(double Latitude, double Longitude, string LocationName, double Confidence)`, set via a new domain method `SetActiveLocation(...)` (mirroring the existing `SetModelSelection` pattern). A new MediatR command `RecordActiveLocationCommand`/`RecordActiveLocationCommandHandler` (mirroring `RecordMemoryReferencesCommand`) is dispatched from `AiController` after the stream completes, only when the trailing chunk carried a `Confirmed` outcome — the same place the controller already reads `chunk.ConfirmedLocation` from today. `LocationResolutionService` reads this value (passed in by the handler, which already fetches the `UserChat` row for the Memory pipeline stage) to resolve a back-reference (FR-014) without a new geocoding call.

**Rationale**: Spec 037's Assumptions explicitly tie this to spec 035's still-unimplemented `ActiveSiteContext` entity, scoped down to only what FR-014 needs — a single last-confirmed-location snapshot, not a full history or the richer metadata (city/district/country/bounding box) 035's entity describes. `UserChat` already carries several similar per-conversation, single-snapshot settings as plain properties (`RetrievalSearchMode`, `RetrievalTopK`, etc.) set via dedicated domain methods and persisted through the same `IUnitOfWork`-per-command convention every other mutating command in this codebase already uses — this feature follows that exact shape rather than introducing a new table or a parallel persistence mechanism. Because `SendChatMessageCommandHandler` is a stream handler and (per its own doc comment and the established codebase convention observed in `AppendMessageCommandHandler`/`RecordMemoryReferencesCommand`) never performs writes itself — all persistence is dispatched as ordinary MediatR commands from the controller after the stream completes — `RecordActiveLocationCommand` follows that same convention rather than writing from inside the handler.

**Alternatives considered**:
- A separate `ChatActiveLocation` table FK'd 1:1 to `UserChat` — rejected: for a single mutable snapshot (not a history), an extra table/join is unjustified complexity per constitution §2.III (KISS/YAGNI) when `UserChat` already models equivalent single-snapshot, per-conversation state as direct properties.
- Deriving "the active location" by re-reading the most recent assistant message's persisted location payload instead of a dedicated snapshot — rejected: that structured per-message persistence is spec 035 FR-016's job, not this feature's; building it here to serve a narrower need would duplicate work a future 035 implementation should own, and would require a message-history query on every turn instead of one property already loaded with the chat.
- Writing the snapshot directly from inside `SendChatMessageCommandHandler` — rejected: breaks the established convention (confirmed by inspecting `AppendMessageCommandHandler`/`AiController`) that this stream handler never persists anything itself; all writes for a turn are explicit, separately-dispatched commands issued by the controller after the stream completes.

## Decision 7 — Every Non-`NoIntent` Outcome Gets a Structured Log Entry (FR-012)

**Decision**: `LocationResolutionService` logs one structured event per resolution attempt via `ILogger<LocationResolutionService>` (Serilog, named properties per constitution §4 "Logging") — `UserChatId`, the extracted query, the chosen outcome type, the winning candidate's source/confidence when applicable, and (for `Unavailable`) the underlying failure reason. `NoIntent` turns are not logged (they are the overwhelming majority of ordinary chat messages and carry no diagnostic value).

**Rationale**: Directly satisfies FR-012 and constitution §2.VIII — the deterministic confirmation text already makes every outcome user-visible; the structured log is what lets an operator later distinguish "the classifier missed an obvious location query" from "the classifier correctly found no intent" from "geocoding was ambiguous/down," none of which are distinguishable from the chat transcript alone.

**Alternatives considered**:
- Logging only failures (`Unavailable`) — rejected: FR-012 explicitly requires logging every attempt (success, ambiguous, not found, timeout, error) to diagnose *missed* detections too, not just outright failures.
