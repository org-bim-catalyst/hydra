# Research: Workflow & Tool Orchestration Engine

**Input**: spec.md (022-workflow-orchestration-engine), the existing implemented codebase for specs 016 (RAG), 018 (Memory), 019 (Prompts), 020 (Agent Framework), 021 (MCP Integration).

Every decision below was made by reading the actual, already-implemented code for specs 016–021 (not their specs/plans in isolation) — this feature lands on a codebase where the Agent Runtime, MCP integration, RAG, Memory, and Prompt engines are real, working modules, not aspirational abstractions. The overriding finding: **the Workflow Engine's job is composition, not reimplementation** — nearly every node type maps onto an existing, already-tested piece of the Agent Runtime.

## Decision 1 — The Workflow Runtime is a new orchestrator that *calls* the existing Agent Runtime; it never re-implements tool execution

**Decision**: `WorkflowExecutionOrchestrator` (new, `Application/Workflows/Runtime/`) is a graph-walking loop, structurally parallel to `AgentExecutionOrchestrator` but driving a deterministic `WorkflowNode` graph instead of an AI-generated linear plan. For every node type except AI Prompt, AI Agent, Condition, Parallel, Merge, Transform, Validation, and Delay, the node's "work" is: resolve an `IAgentTool` instance from the exact same `AgentToolCatalog`/`McpToolRegistry` composition the Agent Runtime already uses, then call `tool.ExecuteAsync(...)` — identical input validation, permission check, approval gate, output validation, and duplicate-call detection as an agent's own tool call, because it is the same call.

**Rationale**: `KnowledgeSearchTool`, `MemorySearchTool`, `DocumentSearchTool`, `FileReadTool`, `FileMetadataTool`, `ConversationTool`, and every `McpToolAdapter`-produced tool already exist, are already tested, and already enforce FR-058's permission-inheritance rule (a `KnowledgeSearchTool` call already intersects the caller's authorized Knowledge Bases; an `McpToolAdapter` call already rate-limits, schema-validates, and redacts credentials). Re-implementing any of this inside the Workflow Engine would be a direct constitution §2.III (DRY) and §18 ("never duplicate business logic that already exists") violation, and spec.md's own Dependencies section forbids it explicitly for RAG (FR-021), Memory (FR-022), MCP (FR-023), and Native tools (FR-024).

**Node → capability mapping**:

| WorkflowNode type | Invocation path | New code |
|---|---|---|
| RAG Search | `KnowledgeSearchTool` via `AgentToolCatalog` | None — reused verbatim |
| Memory Search | `MemorySearchTool` via `AgentToolCatalog` | None — reused verbatim |
| Document Processing | `DocumentSearchTool` via `AgentToolCatalog` | None — reused verbatim |
| File Operation | `FileReadTool`/`FileMetadataTool` via `AgentToolCatalog` | None — reused verbatim (write is out of scope, Decision 4) |
| MCP Tool | `McpToolAdapter`-produced tool via `McpToolRegistry` | None — reused verbatim |
| Native Tool | Any other `AgentToolCatalog` entry (e.g. `ConversationTool`) | None — reused verbatim |
| AI Prompt | `IPromptRepository` + `PromptVariableResolver` + `IAIProvider`/`IAIProviderResolver` | New: `PromptNodeExecutor` (mirrors `AgentExecutionOrchestrator`'s own `ModelReasoning` step, Decision 2) |
| AI Agent | `AgentExecutionOrchestrator.RunAsync` invoked in-process | New: `AgentNodeExecutor` (thin adapter, Decision 3) |
| Condition / Transform / Merge / Validation | New sandboxed expression engine (Decision 6) | New, pure, in-process |
| Parallel | `Task.WhenAll` over branch subgraphs, bounded by `SemaphoreSlim` | New orchestration logic only |
| Human Approval | `WorkflowApproval` (new entity, mirrors `AgentApproval`) | New (Decision 5) |
| Delay | No-op placeholder that validates but never executes a real wait (spec.md: "architectural placeholder for future scheduling") | New, trivial |
| Start / End | Graph structural markers, not executable capability calls | New, trivial |

**Alternatives considered**: A second, workflow-owned tool catalog was rejected — it would immediately drift from the Agent Runtime's permission/risk-level model (exactly the "static-to-dynamic catalog" risk spec.md's Risks section calls out for a different reason) and double the surface area needing security review for identical capabilities.

## Decision 2 — AI Prompt node: reuse `IPromptRepository`/`PromptVariableResolver` for resolution, `IAIProvider`/`IAIProviderResolver` for generation — never a raw provider SDK call

**Decision**: `PromptNodeExecutor` resolves the configured `Prompt`/`PromptVersion` and substitutes variables using the exact same `PromptVariableResolver.ValidateAndResolve`/`ResolveContent` static methods `PromptExecutionTool` (an `IAgentTool`) already uses — this satisfies FR-019's "through the existing Prompt Engine's abstraction." It then calls generation through `IAIProviderResolver.Resolve(providerKey).ChatAsync(...)`, exactly the call `AgentExecutionOrchestrator` already makes for its own `ModelReasoning` steps.

**Rationale**: FR-019 says the node "MUST NOT call an AI provider directly" — read in light of FR-032 (Agent Framework) and constitution §9 ("no Application/Domain code references a specific vendor SDK"), "directly" means bypassing `IAIProvider`, not "the node may never trigger generation at all" (a Prompt node that only resolves text with no model call would be indistinguishable from `PromptExecutionTool`, which already exists and would make the AI Prompt node redundant). `ExecutePromptCommand` (the HTTP-triggered handler backing the Prompt Testing Workspace) was considered and rejected for the same reason `PromptExecutionTool`'s own doc comment rejects it: it depends on `ICurrentUserAccessor`, which never resolves inside a Hangfire background job — the Workflow Runtime runs in exactly that context (Decision 7).

**Alternatives considered**: Delegating to `ExecutePromptCommand` via `ISender.Send` — rejected, would throw `UnauthorizedAccessException` outside an HTTP request, an already-documented dead end in this codebase.

## Decision 3 — AI Agent node: invoke `AgentExecutionOrchestrator.RunAsync` in-process, not `IAgentExecutionRunner.EnqueueAsync`

**Decision**: `AgentNodeExecutor` calls `AgentExecutionOrchestrator.RunAsync(executionId, cancellationToken)` directly (the same pure, Hangfire-decoupled class `IAgentExecutionRunner`'s Hangfire-facing job wraps), inside the Workflow's own background job, and awaits its completion before the workflow node is marked complete. It does not call `IAgentExecutionRunner.EnqueueAsync`, which would schedule a *separate* Hangfire job and return immediately — wrong for a workflow node, whose downstream nodes need the agent's actual output as an input.

**Rationale**: FR-020 requires treating the agent "as an external execution component" without "duplicat[ing] agent planning logic" — calling the existing orchestrator class directly does exactly that: zero planning logic is reimplemented, and the agent's own budget/approval/retry machinery runs unmodified. A workflow-initiated `AgentExecution` row is created exactly as a normal one is (same `AgentExecution.Create`), so it appears in the Agent Framework's own execution history unchanged, satisfying "the workflow engine must coexist with — not replace — the Agent Runtime."

**Consequence for Human Approval nesting**: if the invoked agent itself pauses for approval (its own `AgentExecutionStatus.WaitingForApproval`), `AgentExecutionOrchestrator.RunAsync` returns without completing — the *workflow* node correspondingly transitions to `WaitingForApproval` too (a `WorkflowExecutionNode` state, not a new `WorkflowApproval`, since the approval already belongs to the nested `AgentApproval`). Resuming the workflow after that agent-level approval is decided re-invokes `AgentNodeExecutor` for the same node, which re-calls `RunAsync` on the same `executionId` — an exact mirror of `AgentExecutionOrchestrator`'s own resume path (it already tolerates being called again against a `PlanJson`-populated execution).

**Alternatives considered**: `EnqueueAsync` + poll — rejected as unnecessary indirection (two Hangfire jobs coordinating over polling) when an in-process await is simpler and the orchestrator class was already designed to be called this way (its own doc comment: "callable directly in tests without Hangfire/SignalR").

## Decision 4 — File Operation node ships read/metadata only in v1; no new `FileWriteTool` is introduced

**Decision**: The File Operation node type wraps the existing `FileReadTool`/`FileMetadataTool` only. No general-purpose "write an arbitrary file" `IAgentTool` exists anywhere in the codebase today (writes happen through specific, narrow flows — document upload, memory export — never a generic file-write capability), and inventing one purely to satisfy the spec's generic "reads or writes authorized files" wording would be new, unreviewed, high-risk infrastructure (`WriteFile` permission, `AgentToolPermission.WriteFile` already exists as an enum value but has zero implementing tool) introduced without a concrete use case driving its design.

**Rationale**: constitution §2.III (YAGNI) — "code... MUST NOT be built for hypothetical future requirements not present in an approved specification"; spec.md's own Assumptions section already defers exact tool behavior to "existing platform tool" wrapping, and no existing write-capable tool exists to wrap. If a genuine write use case emerges, it becomes a new `IAgentTool` implementation (zero Workflow Engine changes needed — Decision 1's whole point) reviewed on its own merits, consistent with how `AgentToolPermission.WriteFile` already sits unused in the enum as a reserved value.

**Alternatives considered**: Building a new sandboxed file-write tool now — rejected as scope creep the spec doesn't concretely justify; deferred, not abandoned.

## Decision 5 — Human Approval reuses `AgentApproval`'s *shape and policy-matching algorithm*, not the entity itself; a new `WorkflowApproval` + `WorkflowPolicy` pair, plus one shared extraction

**Decision**: `WorkflowApproval` (new `Domain/Workflows` entity) mirrors `AgentApproval`'s fields (intended action description, parameters, decided-by, decided-at, decision, interactive-vs-policy-based flag) exactly. `WorkflowPolicy` (new) mirrors `AgentPolicy`'s shape (tool/node-type scope, flat JSON conditions, enabled flag). Rather than duplicating `AgentPolicyEvaluator.Matches`'s condition-matching logic verbatim in a new `WorkflowPolicyEvaluator`, that one static method is extracted into a shared `Application/Common/PolicyConditionMatcher.Matches(string? conditionsJson, string inputJson)`, called by both the existing `AgentPolicyEvaluator` and the new `WorkflowPolicyEvaluator`.

**Rationale**: `AgentApproval`/`AgentPolicy` are scoped to a single `AgentExecutionStep` and `AgentToolCall` — a `WorkflowApproval` needs to reference a `WorkflowExecutionNode` instead, so the entities cannot literally be the same row type without a nullable-FK mess spanning two unrelated aggregates (constitution §2.II ISP/ SRP — "one, nameable reason to change"). But the *rule* — "a flat JSON object of parameter constraints, empty means always, every key must equal the actual input" — is identical business logic; leaving it duplicated in two files would violate constitution §2.III DRY the first time one implementation's bug fix isn't mirrored in the other. Extracting it once, called from two evaluators, is the smaller, safer change (three-line extraction, not a new abstraction hierarchy).

**FR-036 (platform-mandatory approval cannot be bypassed)**: enforced identically to the Agent Framework's own equivalent guarantee — `WorkflowExecutionOrchestrator` checks a node's effective risk level (inherited from the underlying `IAgentTool.RiskLevel` it wraps, per Decision 1) against `AgentToolRiskLevel.High`/`Critical` *before* consulting the workflow's own `WorkflowPolicy`; a High/Critical node without a matching policy always pauses, exactly mirroring `AgentExecutionOrchestrator`'s existing `requiresApproval` branch. The workflow author's `WorkflowNode`-level approval configuration (FR-035) can only make approval *more* strict (e.g., "always require for this node") than this baseline, never less.

**Alternatives considered**: Literally reusing `AgentApproval` with a nullable `WorkflowExecutionNodeId` FK alongside its existing `AgentToolCallId` FK — rejected, a row that can belong to either of two unrelated aggregates is the exact "fat, ambiguous entity" constitution §2.II warns against.

## Decision 6 — A new, hand-rolled, closed-grammar expression evaluator; no scripting/eval library is introduced

**Decision**: A new `Application/Workflows/Expressions/WorkflowExpressionEvaluator` parses and evaluates a small, closed expression grammar: literals (string/number/boolean/date/null), variable/step-output references (`{{steps.node_id.output_field}}`, `{{workflow.variable_name}}`), comparison operators (`==`, `!=`, `<`, `<=`, `>`, `>=`), logical operators (`AND`/`OR`/`NOT`) with parentheses/nesting, and a short, explicit whitelist of pure functions (`concat`, `length`, `contains`, `isEmpty`). It is a hand-written recursive-descent parser producing an AST evaluated by direct tree-walking — no `Eval`, no reflection, no dynamic code generation, no loading of arbitrary .NET types.

**Rationale**: FR-027/FR-062 and constitution's "no arbitrary user code" are NON-NEGOTIABLE; general-purpose expression libraries in the .NET ecosystem (Roslyn scripting, DynamicExpresso, NCalc's newer extensible-function variants) are designed to be *extensible* toward arbitrary evaluation, which is exactly the property this feature must not have — auditing "is this closed" for a third-party library is strictly harder than owning a ~200-line grammar with a fixed, reviewed function whitelist. This mirrors research.md Decision 9 from spec 021 (introducing `JsonSchema.Net` only because MCP schemas are genuinely externally-supplied and no safe alternative existed) in reverse: here, a safe alternative (a closed grammar) exists and is simpler than any general-purpose library's threat-modeling burden.

**Type validation (FR-028)**: performed statically at publish/validate time by walking the same AST against each node's declared `WorkflowVariable` types (`Application/Workflows/Validation/WorkflowExpressionTypeChecker`) — a condition comparing a `String` variable against a `Number` literal is a publish-blocking validation error (FR-016), not a runtime surprise.

**Alternatives considered**: NCalc — rejected due to its extensible custom-function/parameter-evaluation hooks being a broader attack surface than this feature needs, and no existing dependency on it in the codebase to justify the risk trade-off; Roslyn `CSharpScript` — rejected outright, arbitrary C# execution is explicitly forbidden by FR-062.

## Decision 7 — Execution runtime: a new Hangfire job (`WorkflowExecutionRunnerJob`/`IWorkflowExecutionRunner`) wrapping a new, pure `WorkflowExecutionOrchestrator`, mirroring `IAgentExecutionRunner`/`AgentExecutionOrchestrator` exactly

**Decision**: `IWorkflowExecutionRunner.EnqueueAsync`/`RunJobAsync` has the identical two-method shape as `IAgentExecutionRunner`; `WorkflowExecutionRunnerJob` is the Hangfire-dispatched `Infrastructure` class; `WorkflowExecutionOrchestrator` is the pure, `Application`-layer step-loop, unit-testable without Hangfire or SignalR. Pause/resume/cancel are implemented identically: an external-status re-check (`executionRepository.GetStatusAsync`) at every node boundary, exactly matching `AgentExecutionOrchestrator`'s own per-step check (its own comment: "observed at every step boundary, not continuously").

**Rationale**: Hangfire is already registered and used for every other long-running, resumable background process in this codebase (`AgentExecutionRunnerJob`, `DocumentProcessingPipeline`, MCP health checks/capability refresh per spec 021 Decision 10) — introducing a second background-job framework for Workflows would violate constitution §2.VII (Convention over Configuration) for no benefit; the pause/resume/status-recheck pattern is already proven correct (spec 020's own SC-009/User Story 4 acceptance tests) and directly satisfies FR-047/FR-048.

**Graph traversal**: unlike `AgentExecutionOrchestrator`'s AI-generated linear `AgentPlan`, `WorkflowExecutionOrchestrator` walks a deterministic DAG derived from `WorkflowConnection` rows — nodes execute once all their dependency edges' source nodes have completed (or been skipped by an unmatched `Condition` branch), computed via a standard topological ordering with cycle detection performed once at publish-time validation (FR-016) so the runtime itself never needs to re-detect cycles.

**Alternatives considered**: A dedicated workflow-engine NuGet package (e.g., Elsa, WorkflowCore) — rejected; pulling in a full third-party workflow runtime would bypass this codebase's own persistence (`BaseEntity`/`RowVersion`/soft-delete), audit, and notification conventions wholesale, the opposite of constitution §2.VII, and would make FR-058's permission-inheritance guarantee (routing every node through the *existing* `IAgentTool` pipeline) far harder to enforce consistently.

## Decision 8 — Real-time: a new `WorkflowExecutionHub` SignalR hub + `WorkflowExecutionNotifier`, mirroring `AgentExecutionHub`/`AgentExecutionNotifier` exactly

**Decision**: New hub/notifier pair, structurally identical to the Agent Framework's, pushing the FR-049 event set (`WorkflowStarted`, `NodeStarted`, `NodeCompleted`, etc.) per-user-group, with the same "persisted `WorkflowExecutionEvent` row is always the reconciliation source of truth if the live push is missed" guarantee `AgentExecutionOrchestrator.RecordAndNotifyAsync` already establishes.

**Rationale**: matches SC-002 (2s node-update visibility) using the same push mechanism that already meets the Agent Framework's equivalent SC-002; no new real-time transport needed (`@microsoft/signalr` is already a frontend dependency). A single shared hub across Agents and Workflows was considered and rejected — `AgentExecutionHub`'s group-naming and payload shapes are agent-specific, and a shared hub would either need type-erasure-y generic payloads (harder to keep type-safe on the frontend) or force the Workflow feature to take on the Agent feature's hub as a dependency, an unnecessary coupling between two sibling features that should stay independently deployable/testable.

## Decision 9 — Parallel execution: in-process `Task.WhenAll` with a `SemaphoreSlim` concurrency gate; no distributed fan-out

**Decision**: A `WorkflowNodeType.Parallel` node's branches execute as concurrent `Task`s within the same Hangfire job process, gated by a `SemaphoreSlim` sized to `min(policy.MaxParallelNodes, options.DefaultMaxParallelNodes)` (mirrors `AgentBudgetGuard`'s policy-then-default fallback pattern exactly). Each branch is itself a sub-walk of the same `WorkflowExecutionOrchestrator` graph-traversal logic, scoped to only the variables/outputs available to it (spec.md Acceptance Scenario 4.2).

**Rationale**: the platform is a single ASP.NET Core deployment with Hangfire server(s) already handling concurrent job execution (constitution §15 "API instances are stateless... scales horizontally"); a single workflow's parallel *branches* are a much smaller unit of concurrency than "run N Hangfire jobs" would imply, and keeping them as in-process `Task`s means the Merge node's four strategies (All/First/Any Completed, Collect All) map directly onto `Task.WhenAll`/`Task.WhenAny`/manual accumulation — no distributed coordination primitive (queue-per-branch, a second job type) is needed for this scope.

**Alternatives considered**: One Hangfire job per branch, coordinated via a Hangfire batch (`IBatchJobClient`) — rejected as unnecessary complexity for in-process-sized parallelism (a handful of branches per node, not thousands); reconsider only if a future scale requirement demands cross-machine branch distribution, which spec.md does not require.

## Decision 10 — Budgets: a new `WorkflowBudgetGuard`, structurally identical to `AgentBudgetGuard`, extended with two workflow-specific limit types

**Decision**: `WorkflowBudgetGuard` checks `MaxNodeCount`, `MaxExecutionDuration`, `MaxTokens`, `MaxCost`, `MaxToolCalls` (four of which are a direct rename of `AgentBudgetGuard`'s existing checks) plus two new checks `AgentBudgetGuard` has no equivalent for: `MaxParallelNodes` (Decision 9's semaphore size) and `MaxLoopIterations` (FR-032's bounded-loop enforcement, checked by the loop-construct's own iteration counter). `WorkflowRuntimeOptions` (new `IOptions<T>` class) mirrors `AgentRuntimeOptions`'s shape (one `[Range]`-validated default per limit) plus `DefaultMaxConcurrentExecutions` for FR-069.

**Rationale**: FR-055's limit set is a near-exact superset of `AgentExecutionPolicy`'s existing limit set (spec.md itself frames workflow budgets in the same vocabulary the Agent Framework already established) — reusing the guard's structure (policy override falls back to a system default, never unbounded) means this feature introduces zero new *pattern*, only two new *values* in an existing pattern.

## Decision 11 — Concurrency cap (FR-069/FR-070): a new `WorkflowUserExecutionLimit`, identical shape to `AgentUserExecutionLimit`

**Decision**: `WorkflowUserExecutionLimit` (new `Domain/Workflows` entity) is a field-for-field copy of `AgentUserExecutionLimit`'s shape (`UserId`, `MaxConcurrentExecutions`, `SetByUserId`), checked the same way `AgentExecutionOrchestrator`'s command-handler-side guard already checks before creating a new `AgentExecution` row — a `WorkflowConcurrencyLimitExceededException` (new, mirrors `AgentConcurrencyLimitExceededException`) is thrown by the `StartWorkflowExecution`/event-trigger-dispatch path before any `WorkflowExecution` row is created, satisfying FR-070's "rejected... rather than silently exceeding the cap."

**Rationale**: this is the exact gap the clarification session (spec.md's Clarifications section) identified by direct analogy to spec 020 FR-042/043 — reusing the identical entity shape and enforcement point means the same administrative UI pattern (an admin sets a per-user override) extends with zero new concepts, only a new table and a new check call-site.

## Decision 12 — Event-Driven triggers: new MediatR post-commit notifications from the Documents/KnowledgeBases modules; no existing domain-event infrastructure to hook into

**Decision**: This codebase does not currently have a working internal domain-event/pub-sub mechanism for "a document was uploaded," "a document finished processing," or "a knowledge base was updated" — those state changes today are only expressed as direct SignalR pushes (`IProcessingNotifier`, `DocumentProcessingHub`) and a feature-scoped `DocumentNotification` row (`docs comment: "No existing in-app notification mechanism was found anywhere in this codebase to reuse"`), neither of which other modules can subscribe to. This feature introduces three small MediatR `INotification` types (`DocumentUploadedNotification`, `DocumentProcessedNotification`, `KnowledgeBaseUpdatedNotification`) published via `ISender`'s sibling `IPublisher` from the *existing* command handlers that already own those state transitions (`UploadDocumentCommandHandler`, the terminal stage of `DocumentProcessingPipeline`, `UpdateKnowledgeBaseCommandHandler` et al.), immediately after their own `SaveChangesAsync` succeeds. A single new `Application/Workflows/EventTriggers/WorkflowEventTriggerHandler : INotificationHandler<T>` (one per event type) matches the event against published, enabled Event-Driven `WorkflowVersion`s whose trigger scope matches (FR-064), checks the scoped user's current authorization and the concurrency cap (Decision 11), and enqueues a `WorkflowExecution` via the same `IWorkflowExecutionRunner.EnqueueAsync` a manual start uses.

**Rationale**: this is the one place in the feature where "extend an existing module's public contract" (constitution §18: "explain architectural trade-offs before implementing a change that... touches more than one architectural layer's public contract") is unavoidable — Event-Driven workflows are impossible to build without *some* signal from Documents/KnowledgeBases. The chosen shape is the smallest possible touch: one `IPublisher.Publish(...)` call added after an already-successful commit in three existing handlers, using MediatR (already a core dependency, already the mechanism the constitution names for cross-cutting concerns) rather than a new pub-sub library or a polling mechanism. This is also, incidentally, the first real instance of the "domain events... dispatched after a successful commit" pattern constitution §3 already mandates but no existing feature actually implements — this feature does not retrofit that pattern onto Documents/KnowledgeBases' *other* state transitions, only the three specific ones FR-063 names.

**Alternatives considered**: Polling (`WorkflowEventTriggerPollingJob` scanning for recently-created documents) — rejected, adds latency against SC-012's 1-minute target and duplicates state-detection logic MediatR notification publishing avoids entirely; a generic platform-wide `IDomainEventDispatcher` retrofit — rejected as disproportionate scope creep for this feature (touches far more than the three event types FR-063 requires) and belongs, if ever undertaken, to its own ADR-backed initiative, not a Workflow Engine spec.

## Decision 13 — Idempotency keys (FR-043): a new nullable `IdempotencyKeyExpression` on `WorkflowNode`, checked against `WorkflowExecutionNode` history before a mutating tool call is retried

**Decision**: A `WorkflowNode` MAY declare an `IdempotencyKeyExpression` (evaluated by the same expression engine, Decision 6). Before `WorkflowExecutionOrchestrator` retries a node whose underlying `IAgentTool.RequiredPermissions` includes a mutating permission (reusing `AgentExecutionOrchestrator`'s own `MutatingPermissions` set — `WriteFile`, `ModifyData`, `SendEmail`, `ExecuteCode`, `HighRiskOperation`, plus the MCP-added external-system equivalents), it resolves the key expression and checks whether a prior `WorkflowExecutionNode` row for this `WorkflowExecution` already recorded a successful attempt with the same resolved key; if so, that prior output is reused and the tool is not called again.

**Rationale**: FR-043 is a genuine new requirement — neither `AgentExecutionOrchestrator`'s retry logic (`ExecuteToolWithRetryAsync`) nor any existing tool has an idempotency concept today, because agent tool retries in spec 020 are scoped to transient provider/network failures within one call, not "the same logical operation attempted again after a full pause/resume cycle" (a workflow-specific scenario: a Human Approval pause, then resume, could otherwise re-invoke an already-succeeded prior node under some execution-policy configurations). Storing the resolved key on `WorkflowExecutionNode` (not a separate table) keeps the check a single indexed lookup within the existing execution-history read path.

**Alternatives considered**: A cache-based idempotency store (e.g., a distributed cache keyed by idempotency key) — rejected as unnecessary infrastructure; the existing per-execution history table already provides exactly the durability and query shape needed, and workflow idempotency is scoped to a single execution, not cross-execution deduplication.

## Decision 14 — Compensation (FR-042): an explicit `CompensatingNodeId` reference on `WorkflowNode`; never inferred

**Decision**: A `WorkflowNode` MAY declare a `CompensatingNodeId` pointing at another node in the same graph (validated at publish time to not itself be reachable in the normal execution path, avoiding a node compensating itself into an infinite loop). When the workflow's failure strategy is `Compensate` and a later node fails, `WorkflowExecutionOrchestrator` walks backward through already-`Completed` nodes in reverse execution order and, for each one that declares a `CompensatingNodeId`, executes that compensating node (through the exact same node-execution path as normal execution — Decision 1's uniform dispatch applies unchanged) before finalizing the execution as `Failed`.

**Rationale**: FR-042 explicitly forbids inferring compensation — this is the literal, minimal mechanism the spec describes ("Create External Record ↓ Later Failure ↓ Delete External Record," "explicitly configured"). No new node-execution machinery is needed; a compensating node is an ordinary node reached through an extraordinary path.

## Decision 15 — Repositories/persistence follow the exact `IAgentRepository`/`Repositories/Agents` shape; one new `AskLucyDbContext` migration

**Decision**: `IWorkflowRepository`, `IWorkflowExecutionRepository`, `IWorkflowPolicyRepository`, `IWorkflowAuditLogRepository` (new, `Application/Abstractions`) mirror `IAgentRepository`/`IAgentExecutionRepository`/`IAgentPolicyRepository`/`IAgentAuditLogRepository` method-for-method (aggregate-oriented methods, no leaky `IQueryable` escape hatch, per constitution §3). `Persistence/Configurations/Workflows/` gets one `IEntityTypeConfiguration<T>` per entity (data-model.md); `Persistence/Repositories/Workflows/` implements the interfaces; one new EF Core migration adds all new tables.

**Rationale**: constitution §3/§5 already fully specify this shape; every prior feature in this codebase (016 through 021) follows it without deviation — there is no decision to make here beyond "follow the established pattern," which is itself the decision worth recording (constitution §2.VII).

## Decision 16 — Frontend: `@xyflow/react` (React Flow) is the new canvas/graph dependency; no existing dependency covers this need

**Decision**: The Workflow Designer canvas (User Story 2) needs node-graph editing (drag-drop nodes, draw/validate typed connections, pan/zoom/minimap, multi-select, undo/redo) that no existing frontend dependency provides — `d3` (already present) is a lower-level visualization primitive used today for particle/chart rendering, not a node-graph editor, and building one from `d3` primitives would be reinventing a well-solved problem. `@xyflow/react` (MIT-licensed, the maintained successor to `react-flow-renderer`, React 19-compatible) is added as the one new npm dependency this feature introduces.

**Rationale**: it is the de facto standard for exactly this UI pattern in the React ecosystem (used by comparable products in this space), ships built-in pan/zoom/minimap/multi-select primitives (directly satisfying FR-010), supports typed/validated edges (FR-008) via its `isValidConnection` hook, and its MIT license clears the project's licensing bar without further review. Node/connection *domain* validation (type compatibility, cycle detection) still runs through the Application-layer contracts (contracts/workflow-node-contract.md), never trusted from the client alone — React Flow only renders and captures the interaction; `ValidateWorkflowCommand` is still the source of truth server-side.

**Alternatives considered**: a bespoke SVG/canvas editor on top of `d3` — rejected, large net-new surface area for a solved problem, directly against constitution §2.III (YAGNI/KISS: "simplest design that satisfies the current, specified requirement"); other graph libraries (e.g., a full BPMN designer) — rejected, spec.md explicitly excludes "Full BPMN compatibility" from scope, and a BPMN-specific library would import a much larger, workflow-notation-specific concept set this feature doesn't need.

## Decision 17 — Any-authenticated-user access (FR-068); no new role or subscription-tier gate

**Decision**: `WorkflowsController`/command handlers apply the same "`[Authorize]` by default, ownership-scoped, no role/tier check" pattern `AgentsController` already uses (spec 020 FR-047's precedent, now spec.md FR-068's direct analogue, confirmed by clarification).

**Rationale**: no `SubscriptionTier`/`Organization` aggregate exists in this codebase (spec 020 Decision 1/2 already established this and deliberately deferred it) — gating Workflow creation by a tier concept that doesn't exist would require inventing exactly the aggregate spec 020 already chose not to build, for a feature that doesn't need it either.

## Decision 18 — Node/step-level schema validation reuses `IJsonSchemaValidator` (`JsonSchema.Net`, introduced by spec 021); no second validator

**Decision**: Every `WorkflowNode`'s declared input/output JSON Schema (FR-017) is validated the same way an MCP tool's externally-supplied schema already is — via the existing `IJsonSchemaValidator` interface (`JsonSchema.Net`-backed, introduced by spec 021 Decision 9) — for nodes whose schema is workflow-author-supplied (Transform, Validation node configuration) rather than inherited from an underlying `IAgentTool` (which already validates its own I/O against its own fixed schema, per Decision 1).

**Rationale**: `JsonSchema.Net` is already a project dependency introduced for exactly this generic "validate untrusted/externally-shaped JSON against a schema" need; a Transform/Validation node's author-defined schema is structurally the same kind of problem MCP tool schemas already solved for, so reusing the interface (not necessarily every call site) avoids introducing a second JSON Schema library.

## Decision 19 — Draft workflow definition is one mutable JSON document on `Workflow`; publishing materializes it into structured, queryable `WorkflowNode`/`WorkflowConnection`/`WorkflowVariable` rows scoped to the new `WorkflowVersion`

**Decision**: While a workflow is being edited, its canvas state (nodes, connections, variables, layout) round-trips as a single `Workflow.DraftDefinitionJson` blob — the Designer naturally edits and saves one graph document, and a draft has no execution history that would ever need to join against an individual node by a stable relational ID. On `Publish`, that JSON is parsed, validated (FR-016), and materialized into real `WorkflowNode`/`WorkflowConnection`/`WorkflowVariable` child rows owned by the new, immutable `WorkflowVersion` — never by `Workflow` directly.

**Rationale**: `AgentVersion`'s own `ToolsSnapshotJson`/`KnowledgeBasesSnapshotJson` fields establish the precedent that a version freezes its associated collections as data, but a workflow graph needs to go one step further than a flat tool list: `WorkflowExecutionNode` (per FR-051's per-node execution history) must FK-reference a specific, individually queryable `WorkflowNode` row — re-parsing a JSON blob on every execution-history read to find "node X's timeout policy" would be exactly the "leaky ad-hoc query" pattern constitution §3 forbids. Materializing structured rows only at publish time (not maintaining two parallel mutable/immutable representations continuously) avoids the two-possible-owner ambiguity Decision 5 explicitly rejected for `WorkflowApproval` — a `WorkflowNode` row belongs to exactly one `WorkflowVersion`, always, once it exists.

**Alternatives considered**: Structured rows for both draft and published state, with a nullable `WorkflowId` XOR `WorkflowVersionId` parent — rejected for the same ambiguous-ownership reason Decision 5 rejected it elsewhere; a fully JSON-only model even for published versions (matching `AgentVersion`'s flat snapshot approach exactly) — rejected because it would force `WorkflowExecutionNode`/`WorkflowApproval`/monitoring queries to parse JSON per read on the platform's highest-cardinality read path (execution history), which the flat-tool-list case (`AgentTool`, a handful of rows) never had to contend with.

## Decision 20 — A bounded loop is a `WorkflowConnection` reserved-label back-edge, not a node-internal-only construct

**Decision**: A bounded loop (FR-032) is an ordinary `WorkflowConnection` whose `BranchLabel` is the reserved value `"loop-back"`, drawn from the loop body's last node back to its first node — exactly the same entity type used for every other edge in the graph, distinguished only by that label. The loop's `MaxIterations`, `TimeoutSeconds`, and failure policy live on the loop body's first node's `ConfigurationJson`, not on the connection itself. `WorkflowGraphValidator`'s cycle detection (FR-016) treats any `"loop-back"`-labeled connection as an intentional, bounded construct and excludes it from the unsupported-cycle check, while still rejecting every other cycle in the graph. At runtime, `WorkflowExecutionOrchestrator` enforces the bound by counting traversals of each `"loop-back"` connection during execution.

**Rationale**: an earlier draft of data-model.md described this ambiguously — in one sentence calling a loop "not a raw graph cycle, expressed through `WorkflowNode.ConfigurationJson`" and in the next calling it a "self-reference" cycle detection must exempt, which are two different designs (loop-as-pure-node-config vs. loop-as-graph-edge) that cannot both be literally true. This decision resolves that ambiguity in favor of the graph-edge representation because: (1) `WorkflowConnection` already has a `BranchLabel` field built for exactly this kind of "this edge means something specific" tagging (it already carries `"true"`/`"false"` for Condition branches), so no schema change is needed; (2) the visual Designer (User Story 2) needs *some* edge on the canvas for a user to draw when connecting a loop body back to its start — a purely config-internal loop would have no visual representation at all, which contradicts FR-032's "e.g., process each item in a collection" framing as something a user builds visually like any other control-flow node; (3) it keeps cycle detection (FR-016) a single, uniform graph algorithm with one well-defined exemption rule, rather than two different code paths (graph-cycle detection plus a separate "is this config secretly a loop" check).

**Alternatives considered**: Loop entirely internal to one node's `ConfigurationJson` (e.g., a single "Loop" node type wrapping its own body as a sub-graph) — rejected; it would require a node type capable of containing a nested sub-graph, a materially different and more complex graph model (nodes-within-nodes) than every other node type in FR-018's list, disproportionate to what FR-032 actually asks for.
