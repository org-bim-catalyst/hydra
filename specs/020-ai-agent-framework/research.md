# Research: AI Agent Framework & Agent Runtime

**Feature**: [spec.md](./spec.md) | **Date**: 2026-08-10

This document resolves every open technical question the spec and constitution leave open, grounded in the actual current state of the codebase (not the aspirational sketches in `docs/ARCHITECTURE.md` §15/§21, `docs/DOMAIN_SERVICES.md` §21, and `docs/ENTITY_MODEL.md` §10/§11, which describe a much simpler placeholder `Agent`/`AgentRun` shape than this feature actually needs — those sections are superseded by this spec and will be rewritten during implementation, not before).

## Decision 1 — Tenant scope for `AgentPolicy`

**Decision**: `AgentPolicy` management is gated by the existing `Administrator`/`Super User` roles (the `AdministratorOrSuperUser` authorization policy already registered in `Program.cs`), not by a new `Organization`/`Tenant` aggregate. `AgentPolicy` carries a reserved, nullable `OrganizationId` column that is always `null` in this release.

**Rationale**: The spec's clarification session committed to `AgentPolicy` being "per-tenant/organization" (FR-025/FR-026), but a repo-wide search confirms **no `Organization`/`Tenant` domain entity exists anywhere in the codebase**. `docs/DATABASE.md` §21 and `docs/ENTITY_MODEL.md` §22 both explicitly list "Organization Accounts"/"Organizations and departments" under **Future Expansion** — multi-tenancy is a deliberately deferred, separately-specified capability, not something this feature should build as a side effect. Today, one Ask Lucy deployment/database *is* the tenant boundary (confirmed by `GetOrganizationDashboardSummaryQuery`, which aggregates across all users in the database and is gated by role, not by any tenant id). A policy an administrator publishes today therefore already cannot "leak" across tenants, because there is only one tenant per deployment — the spec's requirement is satisfied for free by the deployment model. Introducing a new `Organization` aggregate now would be scope creep against YAGNI (constitution §2.III) and would duplicate work a future, dedicated multi-tenancy spec should own.

**Forward compatibility**: the reserved `OrganizationId` column means a future Organization Accounts feature can activate real per-tenant policy scoping via a data migration and an added `WHERE OrganizationId = @current` filter — no `AgentPolicy` schema redesign required (constitution §5 "no future module should require redesigning the existing core schema").

**Alternatives considered**: (a) Build a minimal `Organization` entity now — rejected, out of proportion to this feature's scope and duplicates a capability explicitly reserved for its own future spec. (b) Scope `AgentPolicy` per individual admin user rather than platform-wide — rejected, doesn't match "administrator policy" language in the spec (implies a shared, published policy any admin can see/manage, not a personal one).

## Decision 2 — Subscription-tier dimension for the concurrency cap (FR-042)

**Decision**: FR-042's per-user concurrency cap ships as a **per-user override** for this release: a nullable `MaxConcurrentExecutions` column an administrator can set on a per-user basis, falling back to a system-wide default (`AgentRuntimeOptions.DefaultMaxConcurrentExecutions`, an `IOptions<T>`-bound config value) when unset. No subscription-tier dimension is built.

**Rationale**: A repo-wide search confirms **no subscription-tier/plan entity exists anywhere in the codebase** (`docs/DATABASE.md` §14 and `docs/ENTITY_MODEL.md` §13's `Subscription`/`SubscriptionPlan` sketches were never implemented — Billing is explicitly out of scope for this feature per the spec's own "Out of Scope" list, and FR-047 already commits to no tier-gating for agent creation/execution in this release). Building a `SubscriptionTier` enum solely to serve one config knob would be exactly the kind of premature abstraction constitution §2.III forbids. The per-user override still satisfies FR-042 literally ("configurable per user or subscription tier... by an administrator") — "per user" is one of the two conjuncts the requirement already allows.

**Forward compatibility**: when a real Billing/Subscription feature ships, it can add a tier-default table and have the resolution order become `per-user override → tier default → system default` without changing `AgentExecution`'s own schema.

## Decision 3 — Structured (non-streaming) AI Provider calls for planning and step decisions; streaming for the final user-facing result

**Decision**: The Agent Runtime resolves a provider via `IAIProviderResolver.Resolve(providerKey)` and uses `IAIProvider.ChatAsync(messages, model, parameters, ct)` (the structured, non-streaming overload returning `ChatCompletionResult`) for every internal decision — plan generation, next-step/tool selection, tool-output validation follow-ups — requesting `GenerationParametersDto.JsonMode = true` when `AIModel.SupportsJsonMode` is `true` for the selected model, and falling back to strict-parse-with-one-retry (reusing FR-037's retry policy) when it is not. The final user-facing result for a conversation-integrated execution streams via `IAIProvider.StreamChatAsync(...)`, exactly mirroring `SendChatMessageCommandHandler`/`ExecutePromptCommandHandler`.

**Rationale**: This is the established, only-sanctioned way to call a model in this codebase (`IAIProvider`/`IAIProviderResolver`, `docs/ARCHITECTURE.md` §9) — FR-032 forbids any direct provider SDK call, and `ExecutePromptCommandHandler` is the closest existing precedent for a non-chat, tool-augmented AI call. Using the model/parameter-aware overloads (not the legacy single-arg ones reserved for pre-multi-provider call sites) is required since agents select their model explicitly (FR-001).

**Alternatives considered**: A dedicated "function calling"/tool-use provider feature (native OpenAI/Anthropic tool-call APIs) — rejected for this release; `AIModel.SupportsFunctionCalling` exists as a capability flag but no application code currently exercises it, and building a second, parallel tool-invocation contract per-provider is materially larger scope than the JSON-mode-plus-schema-validation approach, which works uniformly across all four providers today. This can be revisited in a future spec without changing `IAgentTool`'s public contract.

## Decision 4 — RAG and Memory integration reuse existing services verbatim, with a synthetic correlation id

**Decision**: The Knowledge Search tool calls `IRagService.RetrieveContextAsync(correlationId, query, knowledgeBaseIds, ct)`; the Memory Search tool calls `IMemoryService.RetrieveRelevantMemoriesAsync(userId, correlationId, projectId, query, ct)`. In both calls, `correlationId` is a fresh `Guid.CreateVersion7()` minted per tool call — never a real `UserChat`/conversation id unless the execution actually is running inside one (FR-051) — exactly the pattern `ExecutePromptCommandHandler` already established for the Prompt Testing Workspace.

**Rationale**: Both interfaces are the exclusive, already-approved entry points (FR-029/FR-030); neither throws on a retrieval-time failure (`RagRetrievalOutcomeType.Unavailable` / `MemoryRetrievalOutcomeType.Unavailable`), so a Knowledge Search or Memory Search tool call that finds nothing degrades to a normal tool result (`NoRelevantContent`/`Unavailable`) rather than a tool failure — the Agent Runtime does not need special-case error handling for this path, only for a hard exception, which these interfaces are documented never to raise.

Knowledge Base access scoping reuses `IKnowledgeBaseRepository.ResolveOwnedIdsAsync(ownerId, candidateIds, excludeIds, ct)` to compute the authorized id set *before* calling `IRagService`, which is exactly how FR-049 ("an agent's effective access is the intersection of configured + user-authorized, never broader") is already solved elsewhere in the codebase — a requested id the caller doesn't own is silently excluded, never an error or a leak.

## Decision 5 — Memory writes extend the Memory Engine's existing approval lifecycle; the Agent Framework does not build its own

**Decision**: A new command, `CreateMemoryCandidateCommand` (added to `src/AskLucy.Application/Memory/Commands/CreateMemoryCandidate/`, i.e. it extends the Memory feature, not the Agents feature), lets an authorized caller (the Agent Runtime's Memory Write tool) create a `Memory` in `PendingApproval` state via the existing `MemoryApproval.CreatePending(...)` domain factory. The Agent Framework's `MemoryWriteTool` sends this command through `ISender`; it never constructs a `Memory`/`MemoryApproval` row itself.

**Rationale**: `IMemoryService` is read-only (`RetrieveRelevantMemoriesAsync` only) — today the *only* path that creates memory candidates is the passive `MemoryExtractionJob` background sweep. FR-031 ("every memory write MUST be governed by a configurable memory policy... writes outside that policy require explicit user approval") maps directly onto the `Memory` entity's existing `PendingApproval → Active/Rejected` lifecycle and `MemoryCategoryPreference`/`MemoryApprovalMode` policy machinery — reusing it is not duplication, it's the one new integration seam the Memory Engine needs to support an agent-initiated write, and it inherits 100% of the Memory Engine's existing conflict-detection (`IMemoryConflictDetectionService`), category preferences, and privacy controls for free. `AgentMemoryPolicy` (the spec's own entity) governs only whether/when the Agent Framework is willing to *call* `CreateMemoryCandidateCommand` at all (e.g., which categories an agent may propose) — it is not a second, competing approval mechanism; the actual Pending→Active decision still runs through the Memory Engine's existing `ApproveMemory`/`RejectMemory` commands and category-level `Automatic`/`Manual` policy, exactly as it does for extraction-sourced candidates today.

**Risk level implication**: because admission to `Active` memory always still passes through the Memory Engine's own gate, the built-in Memory Write tool defaults to **Medium** risk (not High/Critical) — it creates a proposal, not an immediate mutation — consistent with constitution §8's least-privilege/secure-defaults principle without over-gating a two-layer-approved action.

**Alternatives considered**: Give `IMemoryService` a new `WriteAsync` method directly mutating memory — rejected; it would bypass the conflict-detection and category-preference machinery `MemoryExtractionJob`'s callers rely on, and violates FR-031's "governed by policy" requirement more directly than reusing the existing candidate lifecycle.

## Decision 6 — The Prompt Execution tool delegates to the existing `ExecutePromptCommand`

**Decision**: The Prompt Execution tool (FR-024) sends the existing `ExecutePromptCommand` via `ISender`/`IStreamRequest`, exactly as `InsertPromptIntoConversationCommandHandler` already delegates cross-command via `ISender` rather than reimplementing prompt resolution.

**Rationale**: There is no standalone `IPromptService`; "executing a prompt" is already a MediatR command (`ExecutePromptCommandHandler`) that resolves variables (`PromptVariableResolver`), checks model capabilities (`PromptCapabilityChecker`), and streams a result — all logic FR-033 requires the Agent Framework not to duplicate. Calling the same command is the only way to honor that requirement literally.

## Decision 7 — File tools reuse the Document ownership/storage pattern exactly

**Decision**: File Read and File Metadata tools resolve a file through `IDocumentRepository`, guard access with `DocumentOwnershipGuard.EnsureOwnedBy(document, userId)` (throws `KeyNotFoundException`, mapped to `404` — never `403`, preserving the platform's least-information-disclosure convention), and read content via `IFileStorage.OpenReadAsync(storedFileName, ...)`. Physical storage paths are never exposed to a tool's output.

**Rationale**: This is the same guard every other Document-touching handler in the codebase already uses (`DocumentOwnershipGuard`/`KnowledgeBaseOwnershipGuard`/`ChatOwnershipGuard`/`PromptOwnershipGuard`/`MemoryOwnershipGuard` all share this shape) — reusing it, rather than writing new authorization logic for agent tools, is both less code and automatically consistent with FR-049's access-inheritance requirement.

## Decision 8 — Background execution runs on the existing Hangfire infrastructure

**Decision**: One `AgentExecution` run = one Hangfire background job, dispatched via `BackgroundJob.Enqueue<IAgentExecutionRunner>(runner => runner.RunAsync(executionId, JobCancellationToken.Null))`, mirroring `IDocumentProcessingPipeline`/`DocumentProcessingPipeline` exactly (an injected `IBackgroundJobClient`, not the static `Hangfire.BackgroundJob` facade, at the call site that enqueues — for testability, consistent with the memory note on this exact convention). The runner loops step-by-step, persisting `AgentExecutionStep` state and checking the execution's current status (re-read from the database) before starting each next step; a `Cancel`/`Pause` command updates that status out-of-band, and the runner observes it at the next step boundary and exits (never mid-tool-call). `Resume` and an `Approve`/`Reject` decision each re-enqueue a new Hangfire job continuing from the first non-terminal step — satisfying the spec's "resume interrupted executions where safe" requirement without a custom job-queue mechanism.

**Rationale**: Hangfire (SQL Server storage, the same database) is the only long-running-task mechanism in this codebase — there is no custom `IBackgroundTaskQueue`, no Quartz.NET, no outbox pattern to choose between. `DocumentProcessingPipeline` is the exact structural precedent (a multi-stage pipeline job that persists per-stage outcomes and reports progress over SignalR) — this feature's step-by-step execution loop is the same shape at a different granularity (`AgentExecutionStep` instead of `DocumentProcessingStage`).

**Alternatives considered**: A single long-lived `IHostedService` per execution — rejected; `ProviderHealthCheckHostedService` is the only existing example of that pattern and it's used for continuous polling, not per-request dispatch; it doesn't survive an app restart the way a persisted Hangfire job does, which matters for FR-017's "resumable through status queries" requirement.

## Decision 9 — Real-time execution events use a new SignalR Hub, not Server-Sent Events

**Decision**: A new `AgentExecutionHub : Hub` (in `src/AskLucy.Infrastructure/Agents/`) with a corresponding `IAgentExecutionNotifier` (Application-layer interface) / `AgentExecutionNotifier` (Infrastructure implementation wrapping `IHubContext<AgentExecutionHub>`) pushes the FR-034 event set to per-user SignalR groups, exactly matching `DocumentProcessingHub`/`MemoryHub`/`RetrievalIndexingHub`.

**Rationale**: This corrects the spec's own Assumption ("Server-Sent Events preferred") after research — the codebase already draws a clear, consistent line between the two existing real-time mechanisms: **SSE is used exclusively for a single request's raw AI token stream** (`AiController.Chat`, `PromptsController`'s execute action — both wrap one `IAsyncEnumerable<T>` MediatR stream request over one HTTP response), while **SignalR is used for out-of-band, multi-event, possibly-long-lived progress push tied to a background job** (`DocumentProcessingHub` for the document pipeline, `MemoryHub` for approval/notification events). Agent execution events (`StepStarted`, `ToolCallCompleted`, `ApprovalRequested`, etc.) are structurally identical to `DocumentProcessingStage` progress events, not to a token-by-token generation stream — constitution §2.VII (Convention over Configuration) requires following the established convention for this shape of problem rather than introducing SSE as a second, parallel mechanism for the same use case. This does not conflict with any functional requirement — the spec only requires "real-time" delivery (FR-034, SC-002), not a specific transport — so refining the Assumption here is a normal Phase 0 resolution, not a spec change.

**Alternatives considered**: SSE, as the spec's own (non-binding) Assumption suggested — rejected per the above; would be a second real-time mechanism doing the same job `DocumentProcessingHub`/`MemoryHub` already do, contradicting Convention over Configuration.

## Decision 10 — Tool abstraction is a compile-time-registered `IAgentTool` catalog, not dynamic discovery

**Decision**: `IAgentTool` (Domain or Application — see data-model.md) is implemented by one class per built-in tool (`KnowledgeSearchTool`, `DocumentSearchTool`, `MemorySearchTool`, `PromptExecutionTool`, `FileReadTool`, `FileMetadataTool`, `ConversationTool`), each registered in the DI composition root and resolved by name from an injected `IEnumerable<IAgentTool>` (or a small `IAgentToolCatalog` wrapping that collection). No dynamic/runtime tool discovery mechanism is built.

**Rationale**: MCP (the platform's actual dynamic-tool-discovery mechanism, per `docs/ARCHITECTURE.md` §16) is explicitly out of scope for this feature. A fixed, DI-registered catalog is the simplest design that satisfies FR-020 (tools "discoverable by the Agent Runtime") without building speculative discovery infrastructure for a zero-external-tool release (every FR-024 tool wraps an existing *internal* capability) — consistent with YAGNI.

## Decision 11 — Planning is itself a structured AI Provider call, validated against a fixed JSON schema

**Decision**: `IAgentPlanner.CreatePlanAsync(objective, availableTools, ct)` issues one `IAIProvider.ChatAsync(...)` call (Decision 3) with a system prompt enumerating the agent's available tools (name, description, input schema) and instructions to respond with a JSON plan (goal + ordered steps, each naming a tool or "none"). The response is deserialized and validated against a fixed C# plan-shape contract; an invalid/unparseable response triggers one corrective retry (reusing FR-037's retry budget) before the execution fails with an actionable `AgentExecutionError` ("Invalid Model Response").

**Rationale**: This keeps planning inside the same provider abstraction as everything else (FR-032) and reuses the JSON-mode mechanism from Decision 3, rather than requiring a second, bespoke "planning API." It satisfies FR-012 without inventing a new AI capability.

## Decision 12 — Test executions never invoke a mutating tool; the step is marked `Skipped`, not gated

**Decision**: When `AgentExecution.IsTestExecution` is `true`, the orchestrator does not call `ExecuteAsync` on any tool whose `RequiredPermissions` include a mutating permission (`WriteFile`, `ModifyData`, `SendEmail`, `ExecuteCode`, `HighRiskOperation`) — including the built-in `MemoryWriteTool`. The step is recorded as `AgentExecutionStepStatus.Skipped` with a safe, user-visible reason ("write actions are disabled for test executions"), and no `AgentApproval`/`MemoryApproval` candidate row is created for it.

**Rationale**: SC-007 requires "zero unintended changes to production data" across all test executions. The Assumption already on record ("`Testing` an agent... is still subject to every approval gate... so no production data is modified without the same explicit approval a live run would require") is satisfied more simply and more defensibly by never inserting a row at all than by inserting an inert `PendingApproval` candidate and relying on it never being approved — the latter still leaves a real database write (and a queue-clutter side effect for whichever admin/user reviews pending approvals) as a side effect of a test run, which is a weaker guarantee than "zero changes." Read-only tools (`KnowledgeSearchTool`, `DocumentSearchTool`, `MemorySearchTool`, `FileReadTool`, `FileMetadataTool`, `PromptExecutionTool`, `ConversationTool`) are unaffected and still run normally in test mode, per the existing Assumption. This does not weaken User Story 3's approval-gate testability: quickstart.md's Scenario 3 exercises the approval flow via `FakeHighRiskTool` on a normal (non-test-flagged) execution, not via `isTestExecution: true`, so skip-in-test-mode and interactive-approval-in-production remain two independent, both-tested code paths.

**Alternatives considered**: Allow the write to proceed as a `Pending` candidate (as in Decision 5) even in test mode — rejected per the rationale above; it satisfies the letter of "still requires approval" but not the letter of "zero changes to production data," and constitution §2.III (KISS) favors the simpler "don't call the tool" branch over "call it, then rely on nobody approving the result."

## Technology summary (Technical Context inputs)

| Aspect | Resolution |
|---|---|
| Language/Version | C# on .NET 10 (backend); TypeScript on React 19 + Vite (frontend) — matches every existing feature in this repo |
| Primary Dependencies | MediatR (CQRS), FluentValidation, AutoMapper, Entity Framework Core, Hangfire (background jobs), SignalR (real-time events), ASP.NET Core Identity (auth) — all already present, no new package introduced |
| Storage | SQL Server via EF Core Code-First migrations, `AskLucyDbContext`, following `BaseEntity` (Guid v7 keys, soft delete, audit interceptor, `RowVersion` optimistic concurrency) |
| Testing | xUnit for `.Domain.Tests`/`.Application.Tests`/`.Persistence.Tests`/`.Infrastructure.Tests`/`.Web.Tests`; Playwright (`.spec.ts`) for `.E2E.Tests` — matches every existing feature |
| Target Platform | ASP.NET Core Web API (`AskLucy.Web`) hosting an embedded React SPA (`ClientApp`) — single deployable, no new platform |
| Project Type | Web application (existing modular monolith) — feature adds to the existing five backend projects plus the existing frontend, no new project |
| Performance Goals | SC-002 (≤2s event visibility), SC-009 (≤5s cancel-to-stopped) — achievable with SignalR push (Decision 9) plus a per-step status check in the Hangfire runner (Decision 8) |
| Constraints | No chain-of-thought persistence (FR-035); every tool call permission-checked before execution (FR-022); no direct provider/vector-store/memory-write calls (FR-029/030/032) |
| Scale/Scope | Per-user concurrency capped, admin-configurable, default modest value (Decision 2); no multi-tenant partitioning required this release (Decision 1) |
