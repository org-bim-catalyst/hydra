# Quickstart: Validating the Premium AI SaaS UI/UX Redesign

This guide validates the redesign end-to-end as each application surface ships (FR-013).
It is a manual/runnable validation checklist, not an implementation guide — see
`tasks.md` (generated by `/speckit-tasks`) for the build steps themselves.

## Prerequisites

- Node.js toolchain already used by `src/AskLucy.Web/ClientApp` (see its `package.json`
  engines/scripts — no new tooling is introduced by this feature, per research.md #7).
- Backend (`AskLucy.Web`) running locally so authenticated routes are reachable, since
  this feature does not change auth or API behavior.
- Browser devtools with an accessibility/contrast checker (or the project's existing
  `jest-axe` automated suite, run headlessly — see below) and a way to toggle OS-level
  "reduce motion" (Windows: Settings > Accessibility > Visual effects > Animation effects).

## Setup

```bash
cd src/AskLucy.Web/ClientApp
npm install
npm run dev
```

## Per-page validation (repeat for each Application Surface as it ships — FR-013)

1. **Functional parity** — exercise every pre-existing action on the page (for `/chat`:
   send, edit, regenerate, stop, attach, pin, archive, rename, duplicate, delete, export,
   search) and confirm each produces its prior, correct outcome (SC-002).
2. **Both themes** — toggle light/dark via the existing theme control; confirm no
   unstyled, low-contrast, or mismatched element in either mode (FR-002).
3. **Responsive breakpoints** — resize through mobile/tablet/desktop widths (or use
   devtools device emulation); confirm no cut-off or broken layout (FR-005, SC-004).
4. **Accessibility** — run the page's automated check:
   ```bash
   npm run test -- <PageName>.a11y.test.tsx
   ```
   Zero critical/serious violations (SC-003); then tab through the page with a keyboard
   only and confirm every interactive element is reachable with a visible focus ring
   (FR-004).
5. **Reduced motion** — with the OS "reduce motion" preference enabled, reload the page;
   confirm non-essential animation (transitions, the particle-sphere scene where present)
   is minimized/disabled while the page remains fully usable (FR-010, Edge Cases).
6. **Preserved preferences** — as a user with a previously saved theme/language
   preference, confirm it is still honored after the page's redesign, with no reset
   (FR-011).
7. **Empty / loading / error states** — for any list/panel on the page, trigger each of:
   zero-data, in-flight loading, and a failed request (e.g., via devtools network
   throttling/offline) — confirm a polished `EmptyState`/`SkeletonBlock`/`ErrorState`
   renders for each, never a blank screen (FR-008).
8. **Cross-page consistency** — navigate from this page to one other already-redesigned
   page and back; confirm no jarring change in color, spacing, typography, or navigation
   behavior (SC-007) — this is the manual design sign-off gate research.md #7 relies on in
   place of visual regression tooling.

## Full-suite regression check (run once per page before it ships)

```bash
npm run lint
npm run test
npm run build
```

All three MUST pass with zero new errors/warnings on the changed page's files
(constitution §12) before that Application Surface is marked `verified` per
data-model.md.

## Expected outcome

Every in-scope page (chat, navigation shell, knowledge base, documents, settings, auth,
profile, privacy) independently passes all eight per-page checks above before it ships,
and the whole redesign is complete when every in-scope Application Surface (data-model.md)
is `verified` — admin/internal surfaces are explicitly out of scope (Clarification 1) and
are not part of this quickstart.
